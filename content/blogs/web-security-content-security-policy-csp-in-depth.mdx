## Introduction

Content Security Policy (CSP) is the most powerful browser-based defense against cross-site scripting (XSS), clickjacking, and data injection attacks. By declaring which sources of content are trusted, CSP creates a whitelist that prevents the browser from executing malicious inline scripts, loading unauthorized resources, or submitting data to unexpected endpoints. Despite being over a decade old, CSP remains underutilized—only 5% of websites deploy a meaningful policy.

![Content Security Policy concept](https://images.unsplash.com/photo-1555949963-aa79dcee981c?w=800&h=400&fit=crop)

Modern CSP (Level 3) goes far beyond simple script-src directives. Nonce-based policies, strict-dynamic propagation, and reporting endpoints provide granular control over resource loading while maintaining compatibility with modern JavaScript frameworks. Understanding CSP's directive hierarchy, bypass vectors, and deployment strategies is essential for any security-conscious development team.

This guide covers every CSP directive, implementation patterns for React and Next.js, common bypass techniques attackers use, and production deployment strategies that minimize breakage while maximizing protection.

## Understanding CSP: Core Concepts

CSP operates through HTTP response headers that instruct the browser on which resource origins to trust. When a browser receives a `Content-Security-Policy` header, it enforces the declared restrictions by blocking any resource loading or script execution that violates the policy. Violations can be reported to a server endpoint for monitoring and incident response.

The policy consists of directives, each controlling a specific resource type. The `default-src` directive serves as a fallback for any directive not explicitly declared. For example, `default-src 'self'` restricts all resource loading to the same origin unless a specific directive overrides it.

### The Evolution from CSP Level 1 to Level 3

CSP Level 1 (2012) introduced basic source whitelisting with directives like `script-src`, `style-src`, and `img-src`. It relied on URL-based whitelists and supported `'unsafe-inline'` for inline scripts—essentially a boolean toggle that allowed or blocked inline execution. This first iteration reduced XSS attack surface but left significant gaps, particularly around data exfiltration and clickjacking.

CSP Level 2 (2015) added `frame-ancestors` (replacing the `X-Frame-Options` header), hash-based script whitelisting, and the `report-uri` directive for violation reporting. Hash-based policies allowed specific inline scripts to be approved by their content digest rather than requiring a nonce attribute on every element.

CSP Level 3 (2018, now a W3C Candidate Recommendation) introduced the game-changing `'strict-dynamic'` keyword, `'wasm-unsafe-eval'` for WebAssembly, the `worker-src` directive for controlling Web Worker origins, and the migration from `report-uri` to the Reporting API's `report-to` directive. Level 3 also deprecated `'unsafe-eval'` in favor of more granular controls and added `navigate-to` for restricting form submission and link targets.

### Directive Categories

**Fetch directives** control where resources can be loaded from: `script-src`, `style-src`, `img-src`, `font-src`, `connect-src`, `media-src`, `object-src`, `frame-src`, `worker-src`, `child-src`, `manifest-src`, and `prefetch-src`. Each directive accepts a space-separated list of sources—URLs, scheme expressions (`https:`, `data:`, `blob:`), keywords (`'self'`, `'none'`, `'unsafe-inline'`, `'unsafe-eval'`), nonces (`'nonce-abc123'`), and hashes (`'sha256-xyz...'`).

**Document directives** control the document itself: `base-uri` restricts the URLs that can be used in `<base>` elements (preventing base tag hijacking), `sandbox` enables an HTML5 sandbox on the document, and `form-action` restricts where forms can submit data.

**Navigation directives** control where the user can navigate: `frame-ancestors` specifies valid parents that may embed a page in a `<frame>`, `<iframe>`, `<object>`, `<embed>`, or `<applet>` (replacing `X-Frame-Options`), `navigate-to` restricts the URLs to which a document can initiate navigation, and `form-action` serves dual duty as both a document and navigation directive.

**Reporting directives** handle violation notifications: `report-to` specifies the named endpoint group defined by the `Reporting-Endpoints` HTTP header, and the deprecated `report-uri` specifies a direct URL for violation reports.

### Nonce-Based vs. Hash-Based Policies

Nonce-based policies use a randomly generated token per request, injected as an attribute on trusted inline scripts (`<script nonce="abc123">`). The server generates a unique nonce for each page load and includes it in both the CSP header and the HTML. The nonce must be at least 128 bits of entropy, generated using a cryptographically secure random number generator like `crypto.randomBytes(16)`. Using `Math.random()` or predictable values completely undermines CSP security—attackers who can predict the nonce bypass the entire policy.

Hash-based policies compute the SHA-256 (or SHA-384/SHA-512) digest of specific inline script content and include it in the header. The hash is computed over the exact script content including whitespace and trailing newlines. Hash-based policies work well for static content where the script body doesn't change between deployments. For dynamic content that varies per request (e.g., scripts embedding user data or environment variables), nonces are the correct choice.

The key tradeoff: nonces allow any script with the correct attribute but require server-side generation per request, while hashes allow exactly the specified script content but break if the script changes even by a single character. Both approaches allow trusted inline scripts while blocking injected ones, but nonces integrate better with modern SSR frameworks where script content varies per render.

### The `'strict-dynamic'` Keyword

`'strict-dynamic'` is the centerpiece of modern CSP. When present, it tells the browser to trust any script loaded by an already-trusted script, regardless of the URL origin. This eliminates the need to whitelist every CDN URL, third-party analytics script, and dynamic import. If a script with a valid nonce creates another `<script>` element dynamically, that dynamically created script is also trusted.

Without `'strict-dynamic'`, CSP falls back to source-list evaluation—checking each script's URL against the whitelist. This creates a maintenance nightmare and leaves the door open for injection attacks on whitelisted domains. With `'strict-dynamic'`, the trust chain flows from the initial nonce-bearing script through all its dynamic descendants.

The migration path is: (1) add nonces to all inline scripts, (2) deploy with `'strict-dynamic'` in Report-Only mode, (3) remove unnecessary source whitelist entries, (4) switch to enforcement. During this migration, older browsers that don't support `'strict-dynamic'` fall back to the URL whitelist—you can include both `'strict-dynamic'` and the URLs for backwards compatibility.

## Architecture and Design Patterns

### Component 1: Nonce Generation

Cryptographically secure random nonces must be generated per-request using `crypto.randomBytes(16).toString('base64')`. The nonce flows from the server through the CSP header and into HTML template injection points. The nonce must be at least 128 bits (16 bytes) of entropy and should never be reused across requests. Each page load gets a fresh nonce, which means CSP-protected pages should not be cached by CDNs unless the CDN supports nonce-aware caching (most do not).

### Component 2: Policy Builder

A policy builder constructs the CSP header string from a configuration object, handling directive ordering, value validation, and special keyword merging. This abstraction prevents syntax errors and ensures consistent policies across routes. A well-designed policy builder supports environment-specific overrides—more permissive in development, strictly locked down in production.

### Component 3: Violation Reporting

The `report-uri` (deprecated) and `report-to` directives send violation reports to a designated endpoint. The Reporting API (used by `report-to`) batches violation reports and sends them as JSON payloads containing the violated directive, blocked URI, document referrer, source file, line number, and column number. Processing violation reports reveals both genuine attacks and policy misconfigurations. A sudden spike in violations often indicates an active XSS attempt.

### Component 4: Deployment Pipeline

A phased deployment pipeline starts with `Content-Security-Policy-Report-Only` mode, analyzes violation reports, refines the policy, and gradually enforces restrictions. This prevents accidental breakage in production. The pipeline should include automated CSP header validation in CI/CD to catch syntax errors and policy regressions before deployment.

## Step-by-Step Implementation

### Basic CSP Configuration in Express.js

```typescript
import crypto from 'crypto';
import express from 'express';

const app = express();

// Generate nonce per request
app.use((req, res, next) => {
  res.locals.nonce = crypto.randomBytes(16).toString('base64');
  next();
});

// CSP middleware
app.use((req, res, next) => {
  const nonce = res.locals.nonce;

  const policy = [
    `default-src 'self'`,
    `script-src 'self' 'nonce-${nonce}' 'strict-dynamic'`,
    `style-src 'self' 'unsafe-inline' https://fonts.googleapis.com`,
    `img-src 'self' data: https://images.unsplash.com`,
    `font-src 'self' https://fonts.gstatic.com`,
    `connect-src 'self' https://api.yourdomain.com`,
    `frame-ancestors 'none'`,
    `base-uri 'self'`,
    `form-action 'self'`,
    `report-to csp-endpoint`,
  ].join('; ');

  res.setHeader('Content-Security-Policy', policy);
  next();
});
```

### Nonce Injection for React SSR

```typescript
// pages/_document.tsx
import { Html, Head, Main, NextScript } from 'next/document';
import type { IncomingMessage } from 'http';

interface CustomDocumentProps {
  nonce: string;
}

export default function Document({ nonce }: CustomDocumentProps) {
  return (
    <Html lang="en">
      <Head nonce={nonce}>
        <meta httpEquiv="Content-Security-Policy"
          content={`script-src 'self' 'nonce-${nonce}' 'strict-dynamic'`} />
      </Head>
      <body>
        <Main nonce={nonce} />
        <NextScript nonce={nonce} />
      </body>
    </Html>
  );
}

// middleware.ts — generate nonce per request
import { NextResponse } from 'next/server';
import type { NextRequest } from 'next/server';

export function middleware(request: NextRequest) {
  const nonce = Buffer.from(crypto.randomUUID()).toString('base64');
  const response = NextResponse.next();

  request.headers.set('x-nonce', nonce);
  response.headers.set(
    'Content-Security-Policy',
    `script-src 'self' 'nonce-${nonce}' 'strict-dynamic'; base-uri 'self'; form-action 'self'`
  );

  return response;
}
```

## Common CSP Bypass Techniques

Understanding how attackers circumvent CSP is critical for writing robust policies. Here are the most prevalent bypass vectors:

### Bypass 1: Whitelisted Domain Injection

If your policy whitelists a domain that hosts user-controllable content (e.g., `*.googleapis.com` or a CDN that allows user uploads), attackers can upload a malicious script to that domain and load it via the whitelisted origin. This is the single most common CSP bypass. The fix: use `'strict-dynamic'` with nonces instead of URL whitelists.

### Bypass 2: JSONP Endpoint Abuse

Many whitelisted domains expose JSONP endpoints that execute arbitrary JavaScript. For example, if `https://example.com` is whitelisted and has a `/callback?cb=alert` endpoint, an attacker can inject `<script src="https://example.com/callback?cb=malicious_function">`. Any whitelisted domain with JSONP or open redirect capabilities is a potential bypass vector.

### Bypass 3: Base Tag Hijacking

If `base-uri` is not restricted, an attacker can inject a `<base href="https://attacker.com/">` element, causing all relative URLs in the page to resolve against the attacker's domain. This can redirect form submissions, script loads, and link navigations. Always include `base-uri 'self'` or `base-uri 'none'` in your policy.

### Bypass 4: `object-src` Gaps

If `object-src` is not explicitly set to `'none'`, plugins like Flash or Java applets may load arbitrary content. Even in modern browsers where Flash is deprecated, omitting `object-src` means `default-src` applies—often with a more permissive set of allowed sources. Always set `object-src 'none'` unless you have a specific need for plugin content.

### Bypass 5: `connect-src` Data Exfiltration

If `connect-src` is too permissive, injected scripts can exfiltrate data via `fetch()`, `XMLHttpRequest`, `WebSocket`, or `navigator.sendBeacon()` to attacker-controlled servers. A common mistake is setting `connect-src *` to avoid breaking analytics—this completely undermines data protection. Whitelist only the specific API endpoints your application needs.

### Bypass 6: DOM-Based XSS via Trusted Sinks

CSP protects against injected `<script>` tags and inline event handlers, but DOM-based XSS through `innerHTML`, `eval()`, or `document.write()` can still execute if the CSP doesn't use Trusted Types. The `require-trusted-types-for 'script'` directive forces all DOM XSS sinks to go through a Trusted Types policy, providing an additional layer of protection.

### Bypass 7: Prototype Pollution + Gadgets

Sophisticated attackers use prototype pollution to inject code through "gadget" chains—patterns where a polluted property is later used in an `eval()`-like context. CSP with `'unsafe-eval'` allows these gadgets to execute. Removing `'unsafe-eval'` and using Trusted Types prevents most gadget-based bypasses.

## Real-World Use Cases and Case Studies

### Use Case 1: SaaS Application with Inline Scripts

A SaaS dashboard rendering charts via inline scripts required nonce-based CSP. The team migrated from `'unsafe-inline'` to nonce-based policy by injecting nonces during server-side rendering. After 2 weeks in Report-Only mode, they identified 15 inline scripts that needed noncing and eliminated 3 third-party scripts that couldn't be secured.

### Use Case 2: E-Commerce with Third-Party Widgets

An e-commerce site integrating payment widgets, analytics, and chat support deployed a layered CSP. The initial policy used Report-Only mode for 30 days, revealing 47 third-party domains. The final policy whitelisted only 12 critical domains and removed 8 scripts that violated security requirements.

### Use Case 3: Government Portal with Strict Security

A government portal requiring NIST 800-53 compliance deployed CSP Level 3 with hash-based policies for static content and nonce-based policies for dynamic pages. The deployment included automated CSP validation in CI/CD pipelines, preventing policy regression.

### Use Case 4: Single-Page Application (SPA) with Webpack

A React SPA bundled with Webpack required careful CSP configuration because Webpack injects inline scripts for hot module replacement in development and code splitting in production. The team used `'nonce-{nonce}'` for the development server and `'strict-dynamic'` for production, with separate policy configurations per environment. In development, the Webpack dev server nonce was injected via a custom plugin; in production, the nonce was generated per-request in the CDN edge function.

### Use Case 5: Multi-Tenant Platform

A multi-tenant platform where each tenant could inject custom JavaScript (e.g., tracking scripts, chat widgets) faced a unique CSP challenge. The solution used a two-layer policy: a strict base policy applied to the platform shell, and a tenant-specific policy applied via `<meta>` tags within the tenant's iframe sandbox. This prevented tenant scripts from accessing the platform's DOM or exfiltrating cross-tenant data.

## Best Practices for Production

1. **Start with Report-Only mode**: Deploy `Content-Security-Policy-Report-Only` first and monitor violation reports for 2-4 weeks. Never jump directly to enforcement—misconfigured CSP breaks functionality silently.

2. **Use `'strict-dynamic'` with nonces**: `'strict-dynamic'` trusts scripts loaded by already-trusted scripts, eliminating the need to whitelist every CDN and third-party script URL. This prevents injection attacks on whitelisted domains.

3. **Never use `'unsafe-inline'` for scripts**: `'unsafe-inline'` completely negates CSP's XSS protection. Use nonces or hashes instead. For styles, `'unsafe-inline'` is less dangerous but should still be replaced with nonces when possible.

4. **Implement CSP reporting infrastructure**: Use the Reporting API with `report-to` directive. Tools like Sentry, Report URI, or a custom endpoint aggregate violation reports. Set up alerts for sudden spikes in violations indicating active attacks.

5. **Automate CSP validation in CI/CD**: Add tests that verify CSP headers are present, contain required directives, and don't include `'unsafe-eval'` or `'unsafe-inline'` for scripts. Tools like `csp-validator` catch syntax errors before deployment.

6. **Separate policies per route group**: Admin routes, API endpoints, and public pages have different security requirements. Use middleware to apply route-specific policies rather than one overly permissive global policy.

7. **Document every CSP exception**: Each whitelisted domain or `'unsafe-inline'` usage should have a documented business justification. Regular audits remove exceptions that are no longer needed.

8. **Combine with other security headers**: CSP works best alongside `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, and HSTS.

9. **Set `object-src 'none'` explicitly**: Never rely on `default-src` to restrict plugin content. Explicitly declaring `object-src 'none'` closes a common attack vector.

10. **Include `upgrade-insecure-requests`**: This directive automatically upgrades HTTP subresource requests to HTTPS, preventing mixed content warnings and man-in-the-middle attacks on subresources.

## CSP with Trusted Types

Trusted Types is a browser API that works alongside CSP to prevent DOM XSS entirely. When `require-trusted-types-for 'script'` is added to the CSP, all DOM XSS sinks (`innerHTML`, `outerHTML`, `eval()`, `document.write()`, `setTimeout()` with string arguments, etc.) reject raw strings and require Trusted Types objects instead.

```typescript
// Trusted Types policy prevents DOM XSS in sinks like innerHTML
// Add to CSP: require-trusted-types-for 'script'

import { trustedTypes } from 'trusted-types';

const policy = trustedTypes.createPolicy('sanitize', {
  createHTML: (input: string) => {
    return DOMPurify.sanitize(input);
  },
  createScriptURL: (input: string) => {
    const url = new URL(input, document.baseURI);
    if (url.origin !== location.origin) throw new Error('Blocked script URL');
    return url.toString();
  },
  createScript: (input: string) => {
    // Only allow specific script patterns
    if (/^console\.log/.test(input)) return input;
    throw new Error('Blocked script creation');
  },
});

// Usage — these now go through the sanitizer
element.innerHTML = policy.createHTML(userInput);
script.src = policy.createScriptURL(trustedUrl);
```

The `trusted-types` directive in CSP limits which policy names are allowed:

```
Content-Security-Policy: require-trusted-types-for 'script'; trusted-types sanitize default
```

This means only policies named `'sanitize'` and `'default'` can be created. Any attempt to create a policy with a different name is blocked. In production, `'default'` is the policy used by the browser for implicit sanitization in frameworks that support it.

Trusted Types is supported in Chrome 83+, Edge 83+, and is under development in Firefox and Safari. It's particularly effective for large codebases where auditing every `innerHTML` usage is impractical.

## Common Pitfalls and Solutions

| Pitfall | Impact | Solution |
|---------|--------|----------|
| Deploying enforcement without Report-Only testing | Broken functionality, angry users | Always test in Report-Only mode first |
| Using `'unsafe-inline'` with `'strict-dynamic'` | `'strict-dynamic'` ignores `'unsafe-inline'`, causing unexpected blocks | Remove `'unsafe-inline'` when using nonces + `'strict-dynamic'` |
| Whitelisting `*.googleapis.com` wildcard | Overly broad trust, increases attack surface | Whitelist specific subdomains needed |
| Non-reusable nonces across requests | Broken caching, inconsistent SSR/CSR | Generate per-request nonces, never cache CSP pages with CDN |
| Ignoring CSP violation reports | Missing attack signals and policy misconfigurations | Set up reporting, review weekly, alert on anomalies |
| Using `'self'` for inline styles in SPA | Style bindings blocked, broken UI | Use `'unsafe-inline'` for styles or nonce-based style policy |
| Missing `object-src 'none'` | Plugin-based XSS via Flash/Java applets | Always explicitly set `object-src 'none'` |
| Not setting `base-uri` | Base tag hijacking redirects all relative URLs | Include `base-uri 'self'` or `base-uri 'none'` |
| Forgetting `form-action` | Forms submit to attacker-controlled endpoints | Include `form-action 'self'` |

## Performance Optimization

CSP has minimal runtime overhead—the browser evaluates the policy once per resource load. However, the nonce generation and header injection add latency to server-side rendering. For high-traffic applications, pre-compute nonces in a middleware layer and reuse them across template rendering.

```typescript
// Efficient nonce generation with connection pooling
import { randomBytes } from 'crypto';

const NONCE_CACHE_SIZE = 1000;
const nonceCache: string[] = [];

// Pre-generate nonces in batches
function warmNonceCache(): void {
  const nonces = Array.from({ length: NONCE_CACHE_SIZE }, () =>
    randomBytes(16).toString('base64')
  );
  nonceCache.push(...nonces);
}

// Pop nonces from cache, regenerate when depleted
function getNonce(): string {
  if (nonceCache.length < 100) {
    warmNonceCache();
  }
  return nonceCache.pop()!;
}
```

For CDN-cached pages, consider using edge compute (Cloudflare Workers, Vercel Edge Functions, AWS CloudFront Functions) to generate and inject nonces at the edge. This avoids origin server latency while maintaining per-request nonce uniqueness. The pattern is: cache the HTML body at the origin, and at the edge, replace a nonce placeholder with a freshly generated value and set the CSP header.

## Comparison with Alternatives

| Feature | CSP | SRI (Subresource Integrity) | CORS | Sandbox Iframe |
|---------|-----|---------------------------|------|---------------|
| XSS Prevention | Strong (with nonces) | None | None | Moderate |
| Resource Loading Control | Comprehensive | Per-resource only | Origin-level | Full |
| Inline Script Control | Nonce/hash-based | N/A | N/A | Blocked entirely |
| Third-Party Script Trust | Whitelist + dynamic | Hash verification | Origin check | Full isolation |
| Browser Support | 97%+ | 97%+ | 97%+ | 97%+ |
| Implementation Complexity | High | Low | Medium | Low |

CSP and SRI are complementary—CSP controls which origins can serve scripts, while SRI verifies the content hasn't been tampered with. Using both together provides defense-in-depth against compromised CDNs and supply chain attacks. Add `integrity` attributes to your `<script>` and `<link>` tags alongside CSP nonces for maximum protection.

### CSP for Single-Page Applications

SPAs face unique CSP challenges because content is rendered client-side, styles are often applied via inline attributes, and JavaScript frameworks frequently create dynamic script elements. The recommended pattern is:

```
script-src 'nonce-{nonce}' 'strict-dynamic';
style-src 'self' 'unsafe-inline';
img-src 'self' blob: data: https:;
connect-src 'self' https://api.example.com wss://ws.example.com;
```

For styles, `'unsafe-inline'` is acceptable because CSS injection (while undesirable) is far less dangerous than script injection. Frameworks like styled-components and Emotion inject styles at runtime, making nonce-based style policies impractical without significant refactoring.

### CSP Reporting API Integration

Modern browsers support the Reporting API v1, which replaces the deprecated `report-uri` with a more robust mechanism:

```
Reporting-Endpoints: csp-endpoint="https://report.example.com/csp-reports"
Content-Security-Policy: default-src 'self'; report-to csp-endpoint
```

Violation reports are sent as JSON payloads:

## Testing Strategies

Automated CSP testing should verify header presence, directive correctness, and policy strength:

```typescript
import { test, expect } from '@playwright/test';

test('CSP header is present and enforced', async ({ page }) => {
  const response = await page.goto('/');
  const csp = response?.headers()['content-security-policy'];

  expect(csp).toBeTruthy();
  expect(csp).toContain("script-src 'self'");
  expect(csp).not.toContain("'unsafe-eval'");
  expect(csp).toContain("'strict-dynamic'");
  expect(csp).toContain('report-to');
});

test('inline scripts without nonce are blocked', async ({ page }) => {
  const violations: string[] = [];

  page.on('console', (msg) => {
    if (msg.text().includes('Content-Security-Policy')) {
      violations.push(msg.text());
    }
  });

  await page.evaluate(() => {
    const script = document.createElement('script');
    script.textContent = 'window.__injected = true;';
    document.body.appendChild(script);
  });

  await page.waitForTimeout(500);
  expect(violations.length).toBeGreaterThan(0);
});

test('scripts with valid nonce execute', async ({ page }) => {
  const response = await page.goto('/');
  const csp = response?.headers()['content-security-policy'];
```

## Future Outlook

CSP Level 3 is now a W3C Candidate Recommendation with broad browser support. The `strict-dynamic` keyword, hash-based policies, and the Reporting API represent the current best practice. Emerging features include document-domain deprecation (preventing `document.domain` manipulation), navigational policies (`navigate-to`), and deeper integration with Trusted Types for DOM XSS prevention.

The CSP ecosystem is maturing with better tooling: automated policy generators like [CSP Evaluator](https://csp-evaluator.withgoogle.com/), framework-specific plugins (Next.js, Nuxt), and CI/CD integration. As browsers deprecate `'unsafe-inline'` support for new features, nonce-based policies will become the universal standard.

Looking ahead, the browser ecosystem is moving toward stricter defaults. Chrome has announced plans to restrict `'unsafe-eval'` in certain contexts, and the W3C is working on CSP Level 4 which may include per-document policies, source expressions with wildcards, and tighter integration with the Permissions Policy header. Teams that adopt nonce-based `'strict-dynamic'` policies today will be well-positioned for these changes.

## Conclusion

Content Security Policy is the browser's most powerful defense against XSS and injection attacks, but its effectiveness depends entirely on proper deployment. Start with Report-Only mode, migrate to nonce-based `'strict-dynamic'` policies, build robust violation reporting infrastructure, and automate policy validation. The investment in CSP deployment pays dividends in reduced attack surface and compliance with security frameworks like OWASP, NIST, and SOC 2.

Key implementation checklist: generate cryptographically secure nonces per request (128+ bits of entropy), use `'strict-dynamic'` to avoid whitelist maintenance, always set `object-src 'none'` and `base-uri 'self'`, deploy in Report-Only first, monitor violation reports with the Reporting API, integrate Trusted Types for DOM XSS prevention, and combine with SRI for defense-in-depth. A well-configured CSP, tested thoroughly in Report-Only mode and enforced with strict-dynamic, is one of the single highest-impact security investments a web development team can make.
