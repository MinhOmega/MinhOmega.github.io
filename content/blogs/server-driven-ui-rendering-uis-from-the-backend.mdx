## Introduction

Server-Driven UI (SDUI) is an architecture where the server controls what the client renders. Instead of the client deciding which components to display based on API data, the server sends a UI description that the client interprets. This approach enables instant UI changes without app updates, A/B testing without client deployments, and consistent experiences across platforms.

This guide covers SDUI patterns, implementation strategies, and when to use this architecture.

## What is Server-Driven UI?

In traditional client-driven UI:
1. Client fetches data from an API
2. Client maps data to components
3. Client decides layout and styling

In server-driven UI:
1. Server sends a UI description (components, layout, data)
2. Client renders the description
3. Server controls what appears and how

### When to Use SDUI

**Good use cases:**
- Content-heavy apps (news, e-commerce)
- A/B testing and experimentation
- Apps that need instant UI updates
- Cross-platform consistency (iOS, Android, Web)
- Non-technical teams managing UI

**Not ideal for:**
- Highly interactive apps (games, drawing tools)
- Offline-first applications
- Apps with complex client-side state
- Real-time collaborative tools

### Client Renderer

```typescript
type UIComponent = {
  type: string;
  children?: UIComponent[];
  [key: string]: any;
};

const componentMap: Record<string, React.ComponentType<any>> = {
  screen: Screen,
  column: Column,
  row: Row,
  text: Text,
  image: Image,
  button: Button,
};

function ServerComponent({ node }: { node: UIComponent }) {
  const Component = componentMap[node.type];

  if (!Component) {
    console.warn(`Unknown component type: ${node.type}`);
    return null;
  }

  const { children, ...props } = node;

  return (
    <Component {...props}>
      {children?.map((child, index) => (
        <ServerComponent key={index} node={child} />
      ))}
    </Component>
  );
}
```

### Component Registry

```typescript
// Register components
const registry = new Map<string, React.ComponentType<any>>();

function registerComponent(type: string, component: React.ComponentType<any>) {
  registry.set(type, component);
}

// Register built-in components
registerComponent('text', ({ style, value }) => {
  const styles = {
    heading: { fontSize: 24, fontWeight: 'bold' },
    body: { fontSize: 16 },
    price: { fontSize: 20, color: 'green' },
  };
  return <p style={styles[style] || {}}>{value}</p>;
});

registerComponent('button', ({ label, action, onPress }) => {
  return <button onClick={() => onPress?.(action)}>{label}</button>;
});

registerComponent('image', ({ src, aspectRatio }) => {
  return <img src={src} style={{ aspectRatio, width: '100%' }} />;
});
```

### Screen Builder

```typescript
class ScreenBuilder {
  private screen: UIComponent;

  constructor(title: string) {
    this.screen = { type: 'screen', title, children: [] };
  }

  addHeader(text: string) {
    this.screen.children!.push({
      type: 'text',
      style: 'heading',
      value: text,
    });
    return this;
  }

  addImage(src: string, aspectRatio: number) {
    this.screen.children!.push({
      type: 'image',
      src,
      aspectRatio,
    });
    return this;
  }

  addButton(label: string, action: any) {
    this.screen.children!.push({
      type: 'button',
      label,
      action,
    });
    return this;
  }

  addList(items: any[]) {
    this.screen.children!.push({
      type: 'list',
      items: items.map((item) => ({
        type: 'listItem',
        title: item.title,
        subtitle: item.subtitle,
        image: item.image,
        action: { type: 'navigate', destination: item.url },
      })),
    });
    return this;
  }

  build() {
    return this.screen;
  }
}

// Usage
const screen = new ScreenBuilder('Product List')
  .addHeader('Featured Products')
  .addList(products.map((p) => ({
    title: p.name,
    subtitle: `$${p.price}`,
    image: p.imageUrl,
    url: `/products/${p.id}`,
  })))
  .build();
```

## Handling User Actions

```typescript
// Client-side action handler
function useActionHandler() {
  const navigate = useNavigate();

  return useCallback((action: any) => {
    switch (action.type) {
      case 'navigate':
        navigate(action.destination);
        break;

      case 'addToCart':
        dispatch({ type: 'ADD_TO_CART', productId: action.productId });
        break;

      case 'openUrl':
        window.open(action.url, action.external ? '_blank' : '_self');
        break;

      case 'showModal':
        dispatch({ type: 'SHOW_MODAL', modal: action.modal });
        break;

      case 'api':
        fetch(action.url, {
          method: action.method || 'POST',
          body: JSON.stringify(action.payload),
        });
        break;

      default:
        console.warn(`Unknown action type: ${action.type}`);
    }
  }, [navigate]);
}
```

## Best Practices

1. **Define a clear component schema**: Document all supported component types
2. **Validate server responses**: Client should handle unknown components gracefully
3. **Cache screen definitions**: Reduce server load with caching
4. **Version your schema**: Support backward compatibility
5. **Provide fallbacks**: Handle missing or unknown components

## Common Pitfalls

| Pitfall | Impact | Solution |
|---------|--------|----------|
| No schema validation | Invalid UI states | Validate on both client and server |
| Too many component types | Complex client renderer | Keep component set small and composable |
| No caching | Slow rendering | Cache screen definitions |
| Tight coupling | Hard to evolve | Version your component schema |

### Performance Optimization

Server-driven UI can introduce performance challenges if not implemented carefully. Minimize the size of UI description payloads by using compact formats like Protocol Buffers or MessagePack instead of JSON. Implement caching at the server level so that UI descriptions for common data states are cached and served instantly. Use streaming to send UI descriptions progressively as sections become ready, rather than waiting for the entire description to be generated. On the client, implement lazy rendering so that off-screen components are rendered only when they scroll into view. Profile the rendering pipeline to identify bottlenecks, and optimize the client-side renderer for your most common component types.

### Accessibility Considerations

Server-driven UI must prioritize accessibility to be viable for production applications. Ensure that the UI description format includes all necessary accessibility attributes like ARIA roles, labels, and descriptions. The client-side renderer must map these attributes to the appropriate HTML elements and ARIA properties. Implement keyboard navigation that works correctly with dynamically rendered components. Test with screen readers to verify that server-driven content is announced correctly. Include accessibility testing in your CI pipeline to catch regressions. Consider providing alternative UI descriptions for users who prefer reduced motion or high contrast, which the server can select based on user preferences.

### Component Library Design

Design a comprehensive component library for your server-driven UI system. Define atomic components like text, image, button, and input that map to standard HTML elements. Create composite components like cards, lists, and forms that combine atomic components. Implement layout components like rows, columns, grids, and stacks that control positioning. Each component should have a well-defined schema that specifies its properties, events, and child components. Version your component library independently from your server and client implementations to enable independent evolution. Document each component's schema and behavior so that server developers can use them effectively.

### Error Handling and Fallbacks

Implement robust error handling in your server-driven UI system. When the server sends an unknown component type, the client renderer should display a fallback UI rather than crashing. Handle malformed component descriptions gracefully by logging the error and rendering a placeholder. Implement retry logic for server requests that fail, with exponential backoff to avoid overwhelming the server. Cache the last successful server response so that the client can display stale content when the server is unavailable. These error handling strategies ensure that your application remains functional even when individual components or server requests fail.

### Performance Monitoring

Monitor your server-driven UI system's performance at both the server and client levels. Track server response times for UI description generation to identify slow data sources or complex rendering logic. Monitor client rendering times to ensure that the renderer processes descriptions efficiently. Measure payload sizes to optimize bandwidth usage. Track cache hit rates to verify that your caching strategy is effective. Implement A/B testing to measure the impact of UI changes on user engagement and conversion rates. Use these metrics to continuously improve your server-driven UI system's performance and effectiveness.

Server-driven UI is a powerful pattern that separates the what from the how of user interface rendering. By defining the UI on the server, you gain the ability to iterate rapidly, run experiments, and customize experiences for different user segments. The client becomes a thin rendering layer that interprets the server's instructions, reducing the need for client-side updates when the UI changes. This pattern is particularly valuable for applications that need to support multiple platforms with a consistent experience.

### Offline Support

Implement offline support for server-driven UI applications by caching the last successful server response in IndexedDB. When the device goes offline, the client renderer uses the cached UI description to display content. Implement a service worker that intercepts server requests and returns cached responses when the network is unavailable. Show visual indicators to inform users that they are viewing cached content. When the network connection is restored, automatically fetch fresh UI descriptions and update the display. This offline-first approach ensures that your application remains useful even in environments with unreliable network connectivity, which is particularly important for mobile applications.

### Analytics and Experimentation

One of the most powerful benefits of server-driven UI is the ability to run experiments and analyze user behavior without deploying client updates. Track which UI configurations lead to higher engagement, conversion, and retention rates. Use A/B testing frameworks that operate at the server level to serve different UI descriptions to different user segments. Analyze the results to identify the most effective layouts, component orderings, and interaction patterns. Use these insights to continuously optimize the user experience. This data-driven approach to UI design is particularly valuable for e-commerce, content platforms, and social media applications where small UI changes can have significant business impact.

## Conclusion

Server-Driven UI is a powerful pattern for content-heavy applications that need instant UI updates and cross-platform consistency. By having the server control the UI description, you can A/B test, personalize, and update interfaces without client deployments.

Key takeaways:

1. **Server controls the UI** by sending component descriptions
2. **Client interprets** the description using a component registry
3. **Good for content-heavy apps**: e-commerce, news, dashboards
4. **Cross-platform consistency**: Same UI definition renders on web, iOS, Android
5. **Version your schema** for backward compatibility
