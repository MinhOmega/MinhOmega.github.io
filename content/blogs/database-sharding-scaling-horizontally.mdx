## Introduction

Your database is the bottleneck. Write throughput is maxed out, read replicas can't keep up, and vertical scaling has hit its ceiling. Database sharding—the practice of splitting data across multiple database instances—is the path forward for applications that need to scale beyond what a single machine can handle.

But sharding introduces distributed systems complexity that most teams underestimate. A 2023 survey by CockroachDB found that 67% of teams attempting sharding for the first time experienced production incidents within the first month. The difference between a smooth sharding rollout and a catastrophic one comes down to three decisions: shard key selection, routing architecture, and consistency strategy.

This guide provides a battle-tested approach to sharding, drawn from production systems serving billions of rows across hundreds of shards.

## Understanding Sharding Strategies

### The Three Fundamental Approaches

**Directory-based sharding** maintains a lookup table mapping each key to its shard. This offers maximum flexibility—keys can be moved between shards by updating the directory—but adds a lookup to every query.

**Hash-based sharding** applies a hash function to the key to deterministically select a shard. It's simple and distributes data evenly, but range queries become expensive since consecutive keys may hash to different shards.

**Range-based sharding** assigns contiguous key ranges to each shard. This preserves locality for range queries but can create hot spots if the key space has natural clustering (timestamps, for example).

```sql
-- PostgreSQL native partitioning (range-based)
CREATE TABLE events (
  id BIGINT GENERATED ALWAYS AS IDENTITY,
  user_id UUID NOT NULL,
  event_type VARCHAR(50) NOT NULL,
  payload JSONB,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
) PARTITION BY RANGE (created_at);

-- Monthly partitions
CREATE TABLE events_2024_01 PARTITION OF events
  FOR VALUES FROM ('2024-01-01') TO ('2024-02-01');
CREATE TABLE events_2024_02 PARTITION OF events
  FOR VALUES FROM ('2024-02-01') TO ('2024-03-01');
-- ... automate with pg_partman

-- Hash partitioning for even distribution
CREATE TABLE user_profiles (
  id UUID PRIMARY KEY,
  email VARCHAR(255) NOT NULL,
  profile_data JSONB
) PARTITION BY HASH (id);

CREATE TABLE user_profiles_0 PARTITION OF user_profiles FOR VALUES WITH (MODULUS 8, REMAINDER 0);
CREATE TABLE user_profiles_1 PARTITION OF user_profiles FOR VALUES WITH (MODULUS 8, REMAINDER 1);
-- ... up to user_profiles_7
```

### Shard Key Selection Matrix

| Key Property | Good Example | Bad Example | Why It Matters |
|-------------|-------------|-------------|----------------|
| High cardinality | user_id (millions) | country_code (~200) | Low cardinality creates hot shards |
| Even distribution | UUID, hash of email | Auto-increment ID | Sequential IDs create write hot spots |
| Query locality | tenant_id (multi-tenant) | created_at | Locality reduces cross-shard queries |
| Immutability | user_id | email (can change) | Changing shard key requires data migration |

## Step-by-Step Implementation

### Building a Shard Router

The shard router is the central component that maps shard keys to database connections.

```typescript
import { createHash } from 'crypto';
import { Pool, PoolClient } from 'pg';

interface ShardConfig {
  id: number;
  host: string;
  port: number;
  database: string;
}

class ShardRouter {
  private shards: Map<number, Pool> = new Map();
  private numShards: number;
  private shardConfigs: ShardConfig[];

  constructor(shardConfigs: ShardConfig[]) {
    this.shardConfigs = shardConfigs;
    this.numShards = shardConfigs.length;

    for (const config of shardConfigs) {
      this.shards.set(config.id, new Pool({
        host: config.host,
        port: config.port,
        database: config.database,
        max: 20,
        idleTimeoutMillis: 30000,
        connectionTimeoutMillis: 5000,
      }));
    }
  }

  getShardId(key: string): number {
    const hash = createHash('md5').update(key).digest();
    return hash.readUInt32BE(0) % this.numShards;
  }

  getPool(key: string): Pool {
    return this.shards.get(this.getShardId(key))!;
  }

  async query(key: string, sql: string, params?: any[]): Promise<any[]> {
    const pool = this.getPool(key);
    const result = await pool.query(sql, params);
    return result.rows;
  }

  async transaction<T>(key: string, fn: (client: PoolClient) => Promise<T>): Promise<T> {
    const pool = this.getPool(key);
    const client = await pool.connect();
    try {
      await client.query('BEGIN');
      const result = await fn(client);
      await client.query('COMMIT');
      return result;
    } catch (err) {
      await client.query('ROLLBACK');
      throw err;
    } finally {
      client.release();
    }
  }

  // Scatter-gather across all shards
  async scatterGather(sql: string, params?: any[]): Promise<any[]> {
    const results = await Promise.all(
      Array.from(this.shards.values()).map(pool => pool.query(sql, params))
    );
    return results.flatMap(r => r.rows).sort((a, b) => b.created_at - a.created_at);
  }

  async close(): Promise<void> {
    await Promise.all(Array.from(this.shards.values()).map(pool => pool.end()));
  }
}

// Initialize
const router = new ShardRouter([
  { id: 0, host: 'db-shard-0.internal', port: 5432, database: 'myapp' },
  { id: 1, host: 'db-shard-1.internal', port: 5432, database: 'myapp' },
  { id: 2, host: 'db-shard-2.internal', port: 5432, database: 'myapp' },
  { id: 3, host: 'db-shard-3.internal', port: 5432, database: 'myapp' },
]);
```

### Implementing Global Secondary Indexes

When you need to query by a non-shard key (e.g., finding orders by email when sharded by user_id), you need a global secondary index.

```typescript
// Global index service
class GlobalIndex {
  constructor(
    private indexPool: Pool,  // Separate database for the index
    private router: ShardRouter
  ) {}

  async lookup(indexKey: string, entityType: string): Promise<{ shardId: number; entityId: string }[]> {
    const result = await this.indexPool.query(
      'SELECT shard_id, entity_id FROM global_index WHERE index_key = $1 AND entity_type = $2',
      [indexKey, entityType]
    );
    return result.rows;
  }

  async insert(indexKey: string, entityType: string, shardId: number, entityId: string): Promise<void> {
    await this.indexPool.query(
      'INSERT INTO global_index (index_key, entity_type, shard_id, entity_id) VALUES ($1, $2, $3, $4)',
      [indexKey, entityType, shardId, entityId]
    );
  }

  // Async dual-write pattern: write to shard first, then index
  async createWithIndex(shardKey: string, entity: any, indexKey: string): Promise<any> {
    const result = await router.transaction(shardKey, async (client) => {
      const inserted = await client.query(
        'INSERT INTO orders (user_id, email, total) VALUES ($1, $2, $3) RETURNING *',
        [entity.userId, entity.email, entity.total]
      );
      return inserted.rows[0];
    });

    // Index write can be async via message queue for reliability
    await this.insert(indexKey, 'orders', router.getShardId(shardKey), result.id);

    return result;
  }
}
```

## Real-World Use Cases

### Use Case 1: Multi-Tenant SaaS Sharding

```typescript
// Tenant-aware middleware
import { Request, Response, NextFunction } from 'express';

function tenantShardMiddleware(req: Request, res: Response, next: NextFunction) {
  const tenantId = req.headers['x-tenant-id'] as string;
  if (!tenantId) {
    return res.status(400).json({ error: 'Missing tenant ID' });
  }

  // Attach shard-bound query function to request
  (req as any).shardQuery = (sql: string, params?: any[]) =>
    router.query(tenantId, sql, params);

  (req as any).shardTransaction = <T>(fn: (client: PoolClient) => Promise<T>) =>
    router.transaction(tenantId, fn);

  next();
}

// Usage in route handler
app.get('/api/orders', tenantShardMiddleware, async (req, res) => {
  const orders = await (req as any).shardQuery(
    'SELECT * FROM orders WHERE tenant_id = $1 ORDER BY created_at DESC LIMIT 50',
    [req.headers['x-tenant-id']]
  );
  res.json(orders);
});
```

### Use Case 2: High-Volume Event Ingestion

```typescript
// Batch insert with shard-aware buffering
class EventBuffer {
  private buffers: Map<number, any[]> = new Map();
  private flushInterval: NodeJS.Timeout;

  constructor(private router: ShardRouter, private batchSize: number = 1000) {
    this.flushInterval = setInterval(() => this.flush(), 5000);
  }

  add(event: any): void {
    const shardId = this.router.getShardId(event.user_id);
    if (!this.buffers.has(shardId)) this.buffers.set(shardId, []);
    const buffer = this.buffers.get(shardId)!;
    buffer.push(event);

    if (buffer.length >= this.batchSize) {
      this.flushShard(shardId);
    }
  }

  private async flushShard(shardId: number): Promise<void> {
    const buffer = this.buffers.get(shardId);
    if (!buffer || buffer.length === 0) return;
    this.buffers.set(shardId, []);

    const values = buffer.map((e, i) =>
      `($${i * 4 + 1}, $${i * 4 + 2}, $${i * 4 + 3}, $${i * 4 + 4})`
    ).join(', ');

    const params = buffer.flatMap(e => [e.user_id, e.event_type, JSON.stringify(e.payload), e.created_at]);

    const pool = this.router.getPool(buffer[0].user_id);
    await pool.query(
      `INSERT INTO events (user_id, event_type, payload, created_at) VALUES ${values}`,
      params
    );
  }

  async flush(): Promise<void> {
    await Promise.all(
      Array.from(this.buffers.keys()).map(shardId => this.flushShard(shardId))
    );
  }
}
```

### Use Case 3: Cross-Shard Analytics with Materialized Views

```typescript
// Pre-aggregate shard data into a central analytics database
async function aggregateShardMetrics(): Promise<void> {
  const analyticsPool = new Pool({ host: 'analytics-db.internal' });

  // Query each shard in parallel
  const shardMetrics = await Promise.all(
    Array.from(router['shards'].values()).map(async (pool) => {
      const result = await pool.query(`
        SELECT
          DATE(created_at) as date,
          event_type,
          COUNT(*) as event_count,
          COUNT(DISTINCT user_id) as unique_users
        FROM events
        WHERE created_at >= CURRENT_DATE - INTERVAL '7 days'
        GROUP BY DATE(created_at), event_type
      `);
      return result.rows;
    })
  );

  // Merge and insert into analytics DB
  const merged = new Map<string, any>();
  for (const metrics of shardMetrics) {
    for (const row of metrics) {
      const key = `${row.date}-${row.event_type}`;
      const existing = merged.get(key);
      if (existing) {
        existing.event_count += row.event_count;
        existing.unique_users += row.unique_users;
      } else {
        merged.set(key, { ...row });
      }
    }
  }

  for (const metric of merged.values()) {
    await analyticsPool.query(
      `INSERT INTO daily_metrics (date, event_type, event_count, unique_users)
       VALUES ($1, $2, $3, $4) ON CONFLICT (date, event_type) DO UPDATE
       SET event_count = EXCLUDED.event_count, unique_users = EXCLUDED.unique_users`,
      [metric.date, metric.event_type, metric.event_count, metric.unique_users]
    );
  }
}
```

## Best Practices for Production

1. **Start with more shards than you need**: It's cheaper to have 16 underutilized shards than to reshard from 4 to 16 under pressure. Empty shards cost almost nothing.
2. **Automate shard provisioning**: New shards should be created by infrastructure-as-code, not manual scripts. Use Terraform or Pulumi.
3. **Implement connection pooling per shard**: Use PgBouncer on each shard to manage connection overhead.
4. **Monitor shard health independently**: Each shard needs its own alerting for disk space, replication lag, query latency, and connection count.
5. **Use read replicas for heavy read shards**: Hot shards may need dedicated read replicas for analytics queries.
6. **Implement graceful degradation**: If a shard is unreachable, serve partial results rather than failing entirely.
7. **Version your shard routing**: When adding new shards, old and new routing logic must coexist during migration.
8. **Test with production-like data volumes**: Sharding issues only surface at scale. Load test with realistic data before deploying.

## Common Pitfalls and Solutions

| Pitfall | Impact | Solution |
|---------|--------|----------|
| Choosing auto-increment as shard key | Write hot spot on latest shard | Use UUID or hash of natural key |
| No cross-shard query strategy | Full scatter-gather for common queries | Maintain global secondary indexes |
| Ignoring shard skew | One shard 10x larger than others | Monitor and rebalance proactively |
| Hardcoding shard count | Can't scale without code changes | Use consistent hashing with virtual nodes |
| Missing connection pool limits | Connection exhaustion with many shards | Set per-shard pool max and monitor total |

## Performance Optimization

```typescript
// Connection pool sizing formula
// max_connections = num_shards × pool_size_per_shard + overhead
// PostgreSQL default max_connections = 100
// With 16 shards and 5 connections each = 80 connections + 20 overhead = OK

// Query routing optimization: prefer local shard for multi-key queries
async function batchGetUsers(userIds: string[]): Promise<any[]> {
  // Group by shard
  const byShard = new Map<number, string[]>();
  for (const id of userIds) {
    const shardId = router.getShardId(id);
    if (!byShard.has(shardId)) byShard.set(shardId, []);
    byShard.get(shardId)!.push(id);
  }

  // Parallel query per shard
  const results = await Promise.all(
    Array.from(byShard.entries()).map(([shardId, ids]) => {
      const pool = router['shards'].get(shardId)!;
      return pool.query('SELECT * FROM users WHERE id = ANY($1)', [ids]);
    })
  );

  return results.flatMap(r => r.rows);
}
```

## Resharding Strategies

Resharding—moving data from existing shards to new ones—is the most dangerous operation in a sharded system. Plan for it from day one.

### Consistent Hashing with Virtual Nodes

Simple modulo hashing (`hash(key) % num_shards`) means adding or removing a shard redistributes nearly all data. Consistent hashing minimizes data movement: when you add a shard, only keys from its neighboring shard need to move.

```typescript
class ConsistentHashRouter {
  private ring: { hash: number; shardId: number }[] = [];
  private virtualNodes: number;

  constructor(shardConfigs: ShardConfig[], virtualNodes: number = 150) {
    this.virtualNodes = virtualNodes;

    for (const shard of shardConfigs) {
      for (let i = 0; i < virtualNodes; i++) {
        const hash = this.hash(`${shard.id}-${i}`);
        this.ring.push({ hash, shardId: shard.id });
      }
    }

    this.ring.sort((a, b) => a.hash - b.hash);
  }

  getShardId(key: string): number {
    const hash = this.hash(key);
    // Find the first shard with hash >= key hash (clockwise)
    for (const node of this.ring) {
      if (node.hash >= hash) return node.shardId;
    }
    return this.ring[0].shardId; // Wrap around
  }

  private hash(key: string): number {
    const buffer = createHash('md5').update(key).digest();
    return buffer.readUInt32BE(0);
  }
}
```

With consistent hashing and 150 virtual nodes per shard, adding a 5th shard to a 4-shard cluster moves only ~20% of keys (instead of ~80% with modulo hashing).

### Dual-Write Migration

During resharding, run old and new routing in parallel to verify correctness before cutting over:

```typescript
async function migrateWithDualWrite(key: string, sql: string, params: any[]) {
  // Write to both old and new shard
  const oldShardId = oldRouter.getShardId(key);
  const newShardId = newRouter.getShardId(key);

  const [oldResult, newResult] = await Promise.all([
    oldRouter.query(key, sql, params),
    newRouter.query(key, sql, params),
  ]);

  // Verify consistency
  if (JSON.stringify(oldResult) !== JSON.stringify(newResult)) {
    logger.error('Shard migration mismatch', { key, oldShardId, newShardId });
    await alertOps({ type: 'migration_inconsistency', key });
  }

  return oldResult; // Still read from old during migration
}
```

### Backfill and Cutover

For large datasets, the migration follows a three-phase approach: backfill historical data to new shards (while dual-writing new data), verify consistency with checksums, then cut over reads to the new routing. The backfill runs as a background job that processes keys in batches, respecting rate limits to avoid overwhelming the database.

## Database Performance Tuning

Database performance tuning is an iterative process that requires understanding your query patterns, data distribution, and access frequencies. Small improvements in query performance can have outsized impacts on application responsiveness, especially for frequently executed queries.

### Query Plan Analysis

Always analyze query execution plans before optimizing. In PostgreSQL, use `EXPLAIN ANALYZE` to see both the planned and actual execution statistics:

```sql
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT u.name, COUNT(o.id) as order_count
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE u.created_at > '2024-01-01'
GROUP BY u.id, u.name
ORDER BY order_count DESC
LIMIT 20;
```

Look for sequential scans on large tables (indicating missing indexes), high cost estimates for nested loops (suggesting join strategy issues), and excessive buffer reads (indicating insufficient memory allocation or poor data locality).

### Index Optimization Strategy

Creating the right indexes requires understanding your query patterns. Use `pg_stat_user_tables` and `pg_stat_user_indexes` to identify tables with high sequential scan ratios and unused indexes:

```sql
-- Find tables with high sequential scan ratio
SELECT schemaname, relname, seq_scan, idx_scan,
       CASE WHEN seq_scan + idx_scan > 0
            THEN round(100.0 * idx_scan / (seq_scan + idx_scan), 1)
            ELSE 0 END as idx_usage_pct
FROM pg_stat_user_tables
WHERE seq_scan + idx_scan > 100
ORDER BY idx_usage_pct ASC;

-- Find unused indexes consuming disk space
SELECT indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid))
FROM pg_stat_user_indexes
WHERE idx_scan < 10 AND indexrelname NOT LIKE '%pkey%'
ORDER BY pg_relation_size(indexrelid) DESC;
```

### Connection Pooling Best Practices

Proper connection pooling prevents connection exhaustion under load. Configure your pool size based on your CPU core count and query characteristics:

```
Optimal pool size = (CPU cores * 2) + effective_spindle_count
```

For modern SSD-based systems, this typically means a pool size of `2 * CPU_cores + 1`. Setting the pool too large wastes memory and increases context switching overhead, while setting it too small causes query queuing under load.

## Conclusion

Sharding is a powerful scaling strategy that requires careful planning. Key takeaways:

1. Shard key selection is the most consequential architectural decision—invest heavily in this choice
2. Design for single-shard queries; maintain global indexes for cross-shard access
3. Use consistent hashing to make future scaling non-disruptive
4. Build operational tooling for monitoring, rebalancing, and graceful degradation
5. Consider transparent sharding databases (CockroachDB, Citus) to reduce application complexity

Start by analyzing your query patterns. If most queries can be scoped to a single entity (tenant, user, account), sharding on that entity key will unlock massive scalability.
