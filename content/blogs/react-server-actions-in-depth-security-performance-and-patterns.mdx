## Introduction

React Server Actions are asynchronous functions that run on the server and can be called directly from Client Components. They eliminate the need to create API endpoints for form submissions and data mutations—instead of defining a `POST /api/todos` route and calling `fetch` from your component, you write a server function and call it directly. Under the hood, React serializes the function call into an HTTP request, executes it on the server, and returns the result to the client. This is not a new concept (RPC has existed for decades), but React's implementation is deeply integrated with the framework's rendering lifecycle, form handling, and state management.

Server Actions are powerful but require careful attention to security. Because they are callable from the client, every Server Action is a public API endpoint. Input validation, authentication, and authorization must happen inside the Action—never trust the client. Performance is another consideration: Server Actions block the transition they are called in, so slow Actions make the UI feel sluggish. Understanding how to optimize Actions with caching, revalidation, and streaming is essential for production applications.

This guide covers Server Actions in depth: how they work internally, security best practices, performance optimization patterns, form handling with `useFormState` and `useFormStatus`, optimistic updates with `useOptimistic`, error handling, and advanced patterns for complex applications. By the end, you will understand how to build secure, performant, and maintainable data mutation layers with Server Actions.

## Understanding Server Actions: Core Concepts

### How Server Actions Work

When you define a function with `'use server'`, React creates a reference that can be passed to the client. When the client calls this function, React sends an HTTP POST request to the server with the serialized arguments. The server deserializes the arguments, executes the function, and sends back the result.

```tsx
// app/actions/todo.ts
'use server';

import { revalidatePath } from 'next/cache';
import { db } from '@/lib/db';

export async function createTodo(formData: FormData) {
  const title = formData.get('title') as string;

  // Validation
  if (!title || title.length < 3) {
    return { error: 'Title must be at least 3 characters' };
  }

  // Database operation
  await db.todos.create({ data: { title, completed: false } });

  // Revalidate the page to show new data
  revalidatePath('/todos');

  return { success: true };
}
```

### Inline Server Actions

Server Actions can be defined inline in Server Components. They have closure over the component's props and environment variables.

```tsx
export default function TodoPage() {
  async function addToDo(formData: FormData) {
    'use server';
    const title = formData.get('title');
    await db.todos.create({ data: { title } });
    revalidatePath('/todos');
  }

  return (
    <form action={addToDo}>
      <input name="title" />
      <button type="submit">Add</button>
    </form>
  );
}
```

## Architecture and Design Patterns

### Validation with Zod

Always validate Server Action inputs with a schema validation library. Never trust client data.

```tsx
'use server';

import { z } from 'zod';

const createTodoSchema = z.object({
  title: z.string().min(3).max(200),
  priority: z.enum(['low', 'medium', 'high']).default('medium'),
});

export async function createTodo(formData: FormData) {
  const raw = Object.fromEntries(formData);
  const parsed = createTodoSchema.safeParse(raw);

  if (!parsed.success) {
    return { error: parsed.error.flatten().fieldErrors };
  }

  const todo = await db.todos.create({ data: parsed.data });
  revalidatePath('/todos');
  return { success: true, todo };
}
```

### Authentication and Authorization

Every Server Action must verify authentication and authorization. Treat every Action as a public endpoint.

```tsx
'use server';

import { auth } from '@/lib/auth';

export async function deleteTodo(todoId: string) {
  const session = await auth();
  if (!session?.user) {
    return { error: 'Unauthorized' };
  }

  const todo = await db.todos.findUnique({ where: { id: todoId } });
  if (!todo || todo.userId !== session.user.id) {
    return { error: 'Not found' };
  }

  await db.todos.delete({ where: { id: todoId } });
  revalidatePath('/todos');
  return { success: true };
}
```

## Step-by-Step Implementation

### Form with useFormState

`useFormState` provides the result of the last Server Action invocation, enabling error handling and success feedback without client-side state.

```tsx
'use client';

import { useFormState } from 'react-dom';
import { useFormStatus } from 'react-dom';
import { createTodo } from '@/app/actions/todo';

function SubmitButton() {
  const { pending } = useFormStatus();
  return (
    <button type="submit" disabled={pending}>
      {pending ? 'Creating...' : 'Create Todo'}
    </button>
  );
}

export function CreateTodoForm() {
  const [state, formAction] = useFormState(createTodo, { error: null });

  return (
    <form action={formAction}>
      <input name="title" required />
      {state?.error && <p className="error">{state.error}</p>}
      <SubmitButton />
    </form>
  );
}
```

### Optimistic Updates with useOptimistic

Show the expected result immediately while the Server Action processes in the background.

```tsx
'use client';

import { useOptimistic } from 'react';

function TodoList({ todos }: { todos: Todo[] }) {
  const [optimisticTodos, addOptimisticTodo] = useOptimistic(
    todos,
    (state, newTitle: string) => [
      ...state,
      { id: crypto.randomUUID(), title: newTitle, completed: false, pending: true },
    ]
  );

  async function handleSubmit(formData: FormData) {
    const title = formData.get('title') as string;
    addOptimisticTodo(title);
    await createTodo(formData);
  }

  return (
    <>
      <form action={handleSubmit}>
        <input name="title" required />
        <button type="submit">Add</button>
      </form>
      <ul>
        {optimisticTodos.map(todo => (
          <li key={todo.id} style={{ opacity: todo.pending ? 0.5 : 1 }}>
            {todo.title}
          </li>
        ))}
      </ul>
    </>
  );
}
```

## Real-World Use Cases

### Use Case 1: Multi-Step Form

```tsx
'use server';

export async function submitOrder(formData: FormData) {
  const session = await auth();
  if (!session) return { error: 'Login required' };

  const order = await db.orders.create({
    data: {
      userId: session.user.id,
      items: JSON.parse(formData.get('items') as string),
      shippingAddress: formData.get('address'),
    },
  });

  revalidatePath('/orders');
  redirect(`/orders/${order.id}`);
}
```

### Use Case 2: File Upload

```tsx
'use server';

export async function uploadAvatar(formData: FormData) {
  const session = await auth();
  if (!session) return { error: 'Unauthorized' };

  const file = formData.get('avatar') as File;
  if (file.size > 5 * 1024 * 1024) {
    return { error: 'File must be under 5MB' };
  }

  const buffer = Buffer.from(await file.arrayBuffer());
  const url = await uploadToS3(buffer, file.name);

  await db.users.update({
    where: { id: session.user.id },
    data: { avatarUrl: url },
  });

  revalidatePath('/profile');
  return { success: true, url };
}
```

## Best Practices for Production

1. **Validate every input**: Use Zod or similar to validate all Server Action inputs. Never trust FormData values.
2. **Authenticate and authorize**: Check authentication and resource ownership in every Action.
3. **Return structured results**: Return `{ success, error, data }` objects instead of throwing exceptions for expected failures.
4. **Use revalidation strategically**: Call `revalidatePath` or `revalidateTag` to update cached data after mutations.
5. **Handle errors gracefully**: Use `useFormState` to display error messages without client-side state management.
6. **Use optimistic updates for instant feedback**: `useOptimistic` makes mutations feel instant by showing the expected result before the server responds.
7. **Keep Actions focused**: Each Action should do one thing. Don't create Actions that handle multiple unrelated operations.
8. **Rate limit Server Actions**: Since they are HTTP endpoints, apply rate limiting to prevent abuse.

## Common Pitfalls and Solutions

| Pitfall | Impact | Solution |
|---------|--------|----------|
| No input validation | Security vulnerabilities, data corruption | Use Zod schemas for every Action |
| Missing authentication | Unauthorized data access | Check session in every Action |
| Returning sensitive data | Data leakage | Return only what the client needs |
| No error handling | Silent failures | Return error objects, handle in UI |
| Slow Actions blocking UI | Sluggish feel | Use `useOptimistic` for instant feedback |
| Forgetting revalidation | Stale data displayed | Always revalidate affected paths/tags |

## Performance Optimization

```tsx
// Parallel Server Actions for independent operations
async function handleBulkAction() {
  const [result1, result2] = await Promise.all([
    updateProfile(formData1),
    updateSettings(formData2),
  ]);

// Use revalidation tags for granular cache invalidation
'use server';

export async function updateProduct(id: string, data: ProductData) {
  await db.products.update({ where: { id }, data });
  revalidateTag(`product-${id}`);
  revalidateTag('product-list');
}
```

## Future Outlook

Server Actions are part of React's broader move toward server-first rendering. Combined with React Server Components, they create a model where data fetching and mutations happen on the server by default, and client-side JavaScript is only added where interactivity is needed. The React team is working on improving Server Action performance, adding progress indicators, and enabling better integration with form libraries.

## Conclusion

React Server Actions simplify data mutations by eliminating API endpoint boilerplate and integrating directly with React's form handling and state management. However, their simplicity is deceptive—every Server Action is a public API endpoint that requires proper validation, authentication, and authorization. The key patterns are: validate inputs with Zod, authenticate in every Action, return structured results, use `useFormState` for form feedback, and `useOptimistic` for instant UI updates.

Server Actions are not a replacement for all API endpoints—they are ideal for form submissions and simple mutations. Complex queries, streaming, and external integrations still benefit from dedicated API routes. Use Server Actions where they simplify your code (forms, simple mutations) and traditional APIs where they provide more control (complex queries, webhooks, external integrations).
