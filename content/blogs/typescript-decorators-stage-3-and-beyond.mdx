## Introduction

Decorators are a powerful metaprogramming feature that lets you modify classes, methods, and properties at design time. TypeScript has supported experimental decorators for years, but the TC39 Stage 3 proposal introduces a new standard that differs from the legacy implementation. This guide covers both the legacy and new decorator standards with practical patterns.

## Legacy Decorators (Experimental)

Enable with `experimentalDecorators: true` in tsconfig.json.

### Class Decorators

```typescript
function Sealed(constructor: Function) {
  Object.seal(constructor);
  Object.seal(constructor.prototype);
}

@Sealed
class Greeter {
  greeting: string;
  constructor(message: string) {
    this.greeting = message;
  }
}
```

### Method Decorators

```typescript
function Log(target: any, propertyKey: string, descriptor: PropertyDescriptor) {
  const originalMethod = descriptor.value;

  descriptor.value = function (...args: any[]) {
    console.log(`Calling ${propertyKey} with args:`, args);
    const result = originalMethod.apply(this, args);
    console.log(`Result:`, result);
    return result;
  };

  return descriptor;
}

class Calculator {
  @Log
  add(a: number, b: number): number {
    return a + b;
  }
}
```

### Decorator Factories

```typescript
function Debounce(delay: number) {
  return function (target: any, propertyKey: string, descriptor: PropertyDescriptor) {
    const original = descriptor.value;
    let timer: ReturnType<typeof setTimeout>;

    descriptor.value = function (...args: any[]) {
      clearTimeout(timer);
      timer = setTimeout(() => original.apply(this, args), delay);
    };
  };
}

class SearchService {
  @Debounce(300)
  search(query: string) {
    console.log(`Searching for: ${query}`);
  }
}
```

## Stage 3 Decorators (New Standard)

The new decorator standard doesn't require `experimentalDecorators` and has a different API.

### Basic Class Decorator

```typescript
function logged<T extends new (...args: any[]) => any>(
  target: T,
  context: ClassDecoratorContext
) {
  return class extends target {
    constructor(...args: any[]) {
      super(...args);
      console.log(`Created instance of ${context.name}`);
    }
  };
}

@logged
class User {
  constructor(public name: string) {}
}
```

### Method Decorator

```typescript
function loggedMethod<T extends (...args: any[]) => any>(
  target: T,
  context: ClassMethodDecoratorContext
) {
  return function (this: any, ...args: any[]) {
    console.log(`Calling ${String(context.name)} with`, args);
    return target.apply(this, args);
  };
}

class Calculator {
  @loggedMethod
  add(a: number, b: number) {
    return a + b;
  }
}
```

### Auto-Accessor Decorator

```typescript
function validatePositive<T>(
  target: ClassAccessorDecoratorTarget<any, T>,
  context: ClassAccessorDecoratorContext
) {
  return {
    get(this: any) {
      return target.get.call(this);
    },
    set(this: any, value: T) {
      if (typeof value === 'number' && value <= 0) {
        throw new Error(`${String(context.name)} must be positive`);
      }
      target.set.call(this, value);
    },
  };
}

class Product {
  accessor price: number = 0;

  @validatePositive
  accessor quantity: number = 1;
}
```

## Practical Patterns

### Dependency Injection

```typescript
const injectableMap = new Map<string, any>();

function Injectable(key: string) {
  return function <T extends new (...args: any[]) => any>(target: T) {
    injectableMap.set(key, target);
    return target;
  };
}

function Inject(key: string) {
  return function (target: any, propertyKey: string) {
    Object.defineProperty(target, propertyKey, {
      get: () => injectableMap.get(key),
    });
  };
}

@Injectable('logger')
class Logger {
  log(message: string) {
    console.log(`[LOG] ${message}`);
  }
}

class UserService {
  @Inject('logger') logger!: Logger;

  createUser(name: string) {
    this.logger.log(`Creating user: ${name}`);
  }
}
```

### Memoization

```typescript
function Memoize(target: any, propertyKey: string, descriptor: PropertyDescriptor) {
  const originalMethod = descriptor.value;
  const cache = new Map();

  descriptor.value = function (...args: any[]) {
    const key = JSON.stringify(args);
    if (cache.has(key)) {
      return cache.get(key);
    }
    const result = originalMethod.apply(this, args);
    cache.set(key, result);
    return result;
  };
}

class MathService {
  @Memoize
  fibonacci(n: number): number {
    if (n <= 1) return n;
    return this.fibonacci(n - 1) + this.fibonacci(n - 2);
  }
}
```

### Access Control

```typescript
function Authorize(role: string) {
  return function (target: any, propertyKey: string, descriptor: PropertyDescriptor) {
    const original = descriptor.value;

    descriptor.value = function (...args: any[]) {
      const user = getCurrentUser();
      if (!user || !user.roles.includes(role)) {
        throw new Error('Unauthorized');
      }
      return original.apply(this, args);
    };
  };
}

class AdminController {
  @Authorize('admin')
  deleteUser(userId: string) {
    // Delete user logic
  }
}
```

### Validation

```typescript
function Validate(validator: (value: any) => boolean, errorMessage: string) {
  return function (target: any, propertyKey: string) {
    let value: any;

    Object.defineProperty(target, propertyKey, {
      get: () => value,
      set: (newVal: any) => {
        if (!validator(newVal)) {
          throw new Error(errorMessage);
        }
        value = newVal;
      },
    });
  };
}

class User {
  @Validate((v) => v.length >= 2, 'Name must be at least 2 characters')
  name: string = '';

  @Validate((v) => v.includes('@'), 'Invalid email')
  email: string = '';
}
```

## NestJS Decorators

NestJS makes heavy use of decorators for dependency injection and routing.

```typescript
import { Controller, Get, Post, Body, Injectable, Inject } from '@nestjs/common';

@Injectable()
class UserService {
  findAll() {
    return [{ id: 1, name: 'Alice' }];
  }
}

@Controller('users')
class UserController {
  constructor(private userService: UserService) {}

  @Get()
  findAll() {
    return this.userService.findAll();
  }

  @Post()
  create(@Body() createUserDto: { name: string }) {
    return { id: 2, ...createUserDto };
  }
}
```

## Best Practices

1. **Use decorator factories**: Makes decorators configurable
2. **Keep decorators focused**: Each decorator should do one thing
3. **Document decorator behavior**: Decorators can be non-obvious
4. **Use the new standard**: Stage 3 decorators are the future
5. **Avoid deep nesting**: Too many decorators make code hard to follow

## Common Pitfalls

| Pitfall | Impact | Solution |
|---------|--------|----------|
| Mixing legacy and new | Compilation errors | Use one or the other |
| Decorator execution order | Unexpected behavior | Document and test order |
| this binding issues | Undefined context | Use arrow functions or bind |
| Over-decorating | Hard to understand | Keep decorators simple |

### Testing Decorated Code

Testing code that uses decorators requires understanding how decorators affect the behavior of the decorated declarations. When testing a decorated method, you are testing both the original method and the decorator's behavior. Use dependency injection decorators to replace real services with mocks during testing. Create test-specific decorators that add debugging or assertion logic. When testing decorator composition, verify that the decorators apply in the correct order and that the combined behavior is correct. Use TypeScript's type checking to ensure that decorated declarations maintain their expected types, catching type errors that might be introduced by decorators at compile time.

### Performance Considerations

Decorators add a small runtime overhead because they wrap or modify declarations at class creation time. For most applications, this overhead is negligible. However, in performance-critical code paths where methods are called millions of times per second, the overhead of a logging or validation decorator can become measurable. Profile your application to determine whether decorator overhead is a bottleneck. If it is, consider removing decorators from hot code paths in production builds using conditional compilation or build-time decorator removal. Alternatively, implement lightweight decorators that do minimal work during the hot path and defer expensive operations like logging to a background queue.

### Decorator Patterns

Common decorator patterns include the before-after pattern where a decorator wraps a method to execute code before and after the original method. The memoization pattern caches method results based on their arguments. The throttle and debounce patterns limit how frequently a method can be called. The validation pattern checks method arguments against a schema before execution. The logging pattern records method calls and their results for debugging. The retry pattern automatically retries a failed method call with exponential backoff. These patterns can be combined using decorator composition to create sophisticated behavior from simple building blocks.

### Framework Integration

Modern TypeScript frameworks are adopting stage three decorators. Angular uses decorators extensively for component definition, dependency injection, and lifecycle hooks. NestJS uses decorators for routing, middleware, and validation. TypeORM uses decorators for entity mapping and relationship definition. These frameworks are updating their decorator implementations to use the stage three proposal, which provides a standardized foundation. When using decorators with frameworks, follow the framework's documentation for the correct decorator syntax and behavior. Be aware that some frameworks may still use legacy decorators during the transition period.

### Advanced Decorator Techniques

Advanced decorator techniques include parameter decorators that decorate function parameters rather than the function itself. Use parameter decorators for dependency injection where the decorator determines what value to pass to each parameter based on its type or metadata. Implement accessor decorators that get and set class properties with additional logic like validation, transformation, or lazy loading. Create factory decorators that accept configuration parameters and return a decorator function, enabling reusable decorator configurations. These advanced techniques extend the basic decorator patterns to cover more complex use cases.

### Migration Guide

When migrating your codebase from legacy decorators to stage three decorators, follow this systematic approach. First, update your TypeScript configuration to use the new decorator syntax. Second, identify all files that use legacy decorators and categorize them by complexity. Third, migrate simple decorators like logging and validation first, as they have straightforward equivalents. Fourth, migrate complex decorators that use parameter decorators or property descriptors, which require more refactoring. Fifth, update your tests to verify that the migrated decorators behave correctly. Finally, remove any legacy decorator polyfills or configurations. This incremental approach minimizes risk and allows you to validate each migration step.

### Migration Strategies for Legacy Codebases

Teams with existing codebases using legacy experimental decorators face a significant migration challenge when moving to stage three decorators. The new syntax is incompatible with the old, requiring changes to every decorator declaration and usage. A phased migration approach is recommended: first, upgrade TypeScript to a version that supports both syntaxes simultaneously using the experimentalDecorators compiler option. Then, gradually convert individual decorator declarations from the old syntax to the new, testing each conversion thoroughly. Automated codemods can help with mechanical transformations, but manual review is necessary for complex decorator implementations that rely on legacy features like parameter decorators. The investment in migration pays dividends in terms of improved type safety, better tooling support, and alignment with the official ECMAScript standard.
