## Introduction

Decorators are a powerful metaprogramming feature that lets you modify classes, methods, and properties at design time. TypeScript has supported experimental decorators for years, but the TC39 Stage 3 proposal introduces a new standard that differs from the legacy implementation. This guide covers both the legacy and new decorator standards with practical patterns.

![TypeScript decorators](https://images.unsplash.com/photo-1555066931-4365d14bab8c?w=800&h=400&fit=crop)

Understanding decorators is essential for any TypeScript developer working with frameworks like Angular, NestJS, or TypeORM, all of which rely heavily on decorator-based APIs. In this comprehensive guide, we will explore the history of decorators in JavaScript and TypeScript, examine the differences between the legacy experimental decorators and the new Stage 3 standard, walk through every decorator type with detailed code examples, and provide real-world patterns that you can apply in production codebases.

## A Brief History of Decorators in JavaScript

The decorator proposal has been a long journey in the TC39 process. Originally proposed as a Stage 1 proposal by Yehuda Katz in 2014, decorators were inspired by Python decorators and the annotations system in Java. TypeScript implemented experimental decorators early on based on an earlier version of the proposal, which led to widespread adoption in frameworks like Angular (which launched its decorator-heavy API in Angular 2) and later NestJS.

However, the TC39 proposal went through significant revisions. The original proposal was eventually abandoned in favor of a new approach championed by Ron Buckton. This new approach reached Stage 3 in March 2023, coinciding with the release of TypeScript 5.0. The key difference is that the Stage 3 decorators are designed to be a true ECMAScript standard, while the experimental decorators in TypeScript were based on an older, abandoned version of the proposal.

This history matters because it explains why there are two different decorator systems in TypeScript and why migration is necessary for teams that want to stay aligned with the JavaScript standard.

## Legacy Decorators (Experimental)

Enable with `experimentalDecorators: true` in tsconfig.json. These decorators have been available since TypeScript 1.5 and are still widely used by Angular, NestJS, and TypeORM.

### Class Decorators

A class decorator is applied to the class constructor. It can observe, modify, or replace the class constructor. If a class decorator returns a new constructor, it replaces the original class declaration entirely.

```typescript
function Sealed(constructor: Function) {
  Object.seal(constructor);
  Object.seal(constructor.prototype);
}

@Sealed
class Greeter {
  greeting: string;
  constructor(message: string) {
    this.greeting = message;
  }
}
```

In this example, the `@Sealed` decorator prevents new properties from being added to the `Greeter` class or its prototype at runtime. This is a useful pattern for enforcing immutability constraints on class structures.

### Method Decorators

Method decorators receive three arguments: the target object (for instance members) or the constructor function (for static members), the property key (the name of the method), and the property descriptor. The decorator can modify or replace the property descriptor.

```typescript
function Log(target: any, propertyKey: string, descriptor: PropertyDescriptor) {
  const originalMethod = descriptor.value;

  descriptor.value = function (...args: any[]) {
    console.log(`Calling ${propertyKey} with args:`, args);
    const result = originalMethod.apply(this, args);
    console.log(`Result:`, result);
    return result;
  };

  return descriptor;
}

class Calculator {
  @Log
  add(a: number, b: number): number {
    return a + b;
  }
}
```

When you call `new Calculator().add(2, 3)`, the console will show:
```
Calling add with args: [2, 3]
Result: 5
```

### Decorator Factories

Decorator factories are functions that return a decorator function. They allow you to configure decorator behavior by passing parameters to the factory.

```typescript
function Debounce(delay: number) {
  return function (target: any, propertyKey: string, descriptor: PropertyDescriptor) {
    const original = descriptor.value;
    let timer: ReturnType<typeof setTimeout>;

    descriptor.value = function (...args: any[]) {
      clearTimeout(timer);
      timer = setTimeout(() => original.apply(this, args), delay);
    };
  };
}

class SearchService {
  @Debounce(300)
  search(query: string) {
    console.log(`Searching for: ${query}`);
  }
}
```

The `@Debounce(300)` factory creates a decorator that wraps the `search` method with debounce logic. Only the last call within a 300ms window will actually execute, which is essential for optimizing event handlers like search input or window resize.

### Property Decorators

Property decorators receive the target object and the property key. They are commonly used to define metadata or implement validation patterns.

```typescript
function Required(target: any, propertyKey: string) {
  let value: any;

  const getter = () => value;
  const setter = (newVal: any) => {
    if (newVal === undefined || newVal === null) {
      throw new Error(`${propertyKey} is required`);
    }
    value = newVal;
  };

  Object.defineProperty(target, propertyKey, {
    get: getter,
    set: setter,
    enumerable: true,
    configurable: true,
  });
}

class User {
  @Required
  name!: string;

  @Required
  email!: string;
}
```

### Parameter Decorators

Parameter decorators are unique to the legacy experimental decorator system and have no equivalent in the Stage 3 standard. They receive the target, the method name, and the parameter index.

```typescript
function LogParam(target: any, methodName: string, paramIndex: number) {
  const existingParams: number[] = Reflect.getOwnMetadata('logParams', target, methodName) || [];
  existingParams.push(paramIndex);
  Reflect.defineMetadata('logParams', existingParams, target, methodName);
}

class UserService {
  getUser(@LogParam userId: string) {
    return { id: userId, name: 'Alice' };
  }
}
```

Parameter decorators require the `reflect-metadata` polyfill and are heavily used by Angular for dependency injection. The absence of parameter decorators in the Stage 3 standard is one of the biggest migration challenges for Angular and NestJS.

## Stage 3 Decorators (New Standard)

TypeScript 5.0 introduced support for the Stage 3 decorator proposal. These decorators do not require `experimentalDecorators` and provide a different API that aligns with the ECMAScript specification.

### Key Differences from Legacy Decorators

The Stage 3 decorators differ from legacy decorators in several important ways:

1. **No parameter decorators** — The Stage 3 proposal does not include parameter decorators. Frameworks that rely on them (like Angular) must use alternative approaches.
2. **Context objects** — Instead of receiving raw arguments, decorators receive a context object that provides metadata about the decorated declaration.
3. **Initializer functions** — Instead of modifying property descriptors directly, decorators return initializer functions that are called to initialize the declaration.
4. **`access` keyword** — Stage 3 introduces `accessor` keyword for auto-accessor properties, which provide getter/setter hooks at the class field level.
5. **No `return descriptor` pattern** — Legacy decorators often returned modified descriptors; Stage 3 decorators return new values or initializers.

### Basic Class Decorator

```typescript
function logged<T extends new (...args: any[]) => any>(
  target: T,
  context: ClassDecoratorContext
) {
  return class extends target {
    constructor(...args: any[]) {
      super(...args);
      console.log(`Created instance of ${context.name}`);
    }
  };
}

@logged
class User {
  constructor(public name: string) {}
}
```

In this example, the `@logged` decorator receives the class constructor as `target` and a `ClassDecoratorContext` object. The context provides the class `name`, the `kind` (always `"class"`), and metadata capabilities. The decorator returns a new class that extends the original, adding logging to the constructor.

### Method Decorator

```typescript
function loggedMethod<T extends (...args: any[]) => any>(
  target: T,
  context: ClassMethodDecoratorContext
) {
  return function (this: any, ...args: any[]) {
    console.log(`Calling ${String(context.name)} with`, args);
    return target.apply(this, args);
  };
}

class Calculator {
  @loggedMethod
  add(a: number, b: number) {
    return a + b;
  }
}
```

The method decorator receives the original method as `target` and a `ClassMethodDecoratorContext` that provides the method `name`, whether it is `static`, `private`, or `accessor`, and whether it is `"method"` or `"getter"`/`"setter"` kind.

### Auto-Accessor Decorator

Auto-accessors are a new feature introduced alongside Stage 3 decorators. The `accessor` keyword creates a field with an automatically generated getter and setter, which decorators can intercept.

```typescript
function validatePositive<T>(
  target: ClassAccessorDecoratorTarget<any, T>,
  context: ClassAccessorDecoratorContext
) {
  return {
    get(this: any) {
      return target.get.call(this);
    },
    set(this: any, value: T) {
      if (typeof value === 'number' && value <= 0) {
        throw new Error(`${String(context.name)} must be positive`);
      }
      target.set.call(this, value);
    },
  };
}

class Product {
  accessor price: number = 0;

  @validatePositive
  accessor quantity: number = 1;
}
```

Auto-accessor decorators receive the original `{ get, set }` target and can wrap both the getter and setter with additional logic. This is significantly cleaner than the legacy approach of using property decorators with `Object.defineProperty`.

### Field Decorator

Field decorators receive the initial value (or `undefined` if none is provided) as the target and a `ClassFieldDecoratorContext`. They can return an initializer function that transforms the value during class instantiation.

```typescript
function minLength(min: number) {
  return function (target: undefined, context: ClassFieldDecoratorContext) {
    return function (initialValue: string) {
      if (initialValue.length < min) {
        throw new Error(`${String(context.name)} must be at least ${min} characters`);
      }
      return initialValue;
    };
  };
}

class Article {
  @minLength(10)
  title: string = "Default Title";
}
```

### Decorator Execution Order

Understanding decorator execution order is crucial for avoiding subtle bugs. In Stage 3 decorators:

- **Decorators execute bottom-up** — When multiple decorators are applied to the same declaration, the bottom decorator runs first.
- **Initializers execute top-down** — After all decorators have been processed, their returned initializer functions execute in top-down (declaration) order.
- **Class decorators execute after all member decorators** — All method, field, and accessor decorators on the class are processed before the class decorator runs.

```typescript
function first() {
  return function (target: any, context: ClassMethodDecoratorContext) {
    console.log("first decorator applied");
    return function (this: any, ...args: any[]) {
      console.log("first initializer runs");
      return target.apply(this, args);
    };
  };
}

function second() {
  return function (target: any, context: ClassMethodDecoratorContext) {
    console.log("second decorator applied");
    return function (this: any, ...args: any[]) {
      console.log("second initializer runs");
      return target.apply(this, args);
    };
  };
}

class Example {
  @first()
  @second()
  method() {}
}

// Output during class declaration:
// "second decorator applied"
// "first decorator applied"

// Output during method call:
// "first initializer runs"
// "second initializer runs"
```

## Practical Patterns

### Dependency Injection

A lightweight dependency injection container using decorators:

```typescript
const injectableMap = new Map<string, any>();

function Injectable(key: string) {
  return function <T extends new (...args: any[]) => any>(target: T) {
    injectableMap.set(key, target);
    return target;
  };
}

function Inject(key: string) {
  return function (target: any, propertyKey: string) {
    Object.defineProperty(target, propertyKey, {
      get: () => injectableMap.get(key),
    });
  };
}

@Injectable('logger')
class Logger {
  log(message: string) {
    console.log(`[LOG] ${message}`);
  }
}

class UserService {
  @Inject('logger') logger!: Logger;

  createUser(name: string) {
    this.logger.log(`Creating user: ${name}`);
  }
}
```

This pattern forms the foundation of how frameworks like NestJS handle dependency injection. In NestJS, the `@Injectable()` decorator marks a class as a provider that can be injected, while `@Inject()` retrieves instances from the IoC (Inversion of Control) container.

### Memoization

Cache expensive method results based on their arguments:

```typescript
function Memoize(target: any, propertyKey: string, descriptor: PropertyDescriptor) {
  const originalMethod = descriptor.value;
  const cache = new Map();

  descriptor.value = function (...args: any[]) {
    const key = JSON.stringify(args);
    if (cache.has(key)) {
      return cache.get(key);
    }
    const result = originalMethod.apply(this, args);
    cache.set(key, result);
    return result;
  };
}

class MathService {
  @Memoize
  fibonacci(n: number): number {
    if (n <= 1) return n;
    return this.fibonacci(n - 1) + this.fibonacci(n - 2);
  }
}
```

Without `@Memoize`, the `fibonacci(40)` call would make over a billion recursive calls. With memoization, each unique argument is computed only once, reducing the complexity from exponential to linear.

### Access Control

Implement role-based access control with decorators:

```typescript
function Authorize(role: string) {
  return function (target: any, propertyKey: string, descriptor: PropertyDescriptor) {
    const original = descriptor.value;

    descriptor.value = function (...args: any[]) {
      const user = getCurrentUser();
      if (!user || !user.roles.includes(role)) {
        throw new Error('Unauthorized');
      }
      return original.apply(this, args);
    };
  };
}

class AdminController {
  @Authorize('admin')
  deleteUser(userId: string) {
    // Delete user logic
  }
}
```

### Validation with Property Decorators

```typescript
function Validate(validator: (value: any) => boolean, errorMessage: string) {
  return function (target: any, propertyKey: string) {
    let value: any;

    Object.defineProperty(target, propertyKey, {
      get: () => value,
      set: (newVal: any) => {
        if (!validator(newVal)) {
          throw new Error(errorMessage);
        }
        value = newVal;
      },
    });
  };
}

class User {
  @Validate((v) => v.length >= 2, 'Name must be at least 2 characters')
  name: string = '';

  @Validate((v) => v.includes('@'), 'Invalid email')
  email: string = '';
}
```

### Rate Limiting Decorator

A practical example for API endpoints or expensive operations:

```typescript
function RateLimit(maxCalls: number, windowMs: number) {
  return function (target: any, propertyKey: string, descriptor: PropertyDescriptor) {
    const original = descriptor.value;
    const calls: number[] = [];

    descriptor.value = function (...args: any[]) {
      const now = Date.now();
      const windowStart = now - windowMs;

      // Remove expired entries
      while (calls.length > 0 && calls[0] < windowStart) {
        calls.shift();
      }

      if (calls.length >= maxCalls) {
        throw new Error(`Rate limit exceeded for ${propertyKey}: ${maxCalls} calls per ${windowMs}ms`);
      }

      calls.push(now);
      return original.apply(this, args);
    };
  };
}

class PaymentService {
  @RateLimit(10, 60000)
  processPayment(amount: number) {
    // Process payment logic
  }
}
```

### Retry with Exponential Backoff

```typescript
function Retry(maxRetries: number = 3, baseDelay: number = 1000) {
  return function (target: any, propertyKey: string, descriptor: PropertyDescriptor) {
    const original = descriptor.value;

    descriptor.value = async function (...args: any[]) {
      let lastError: Error | undefined;

      for (let attempt = 0; attempt <= maxRetries; attempt++) {
        try {
          return await original.apply(this, args);
        } catch (error) {
          lastError = error as Error;
          if (attempt < maxRetries) {
            const delay = baseDelay * Math.pow(2, attempt);
            console.log(`Retry ${attempt + 1}/${maxRetries} for ${propertyKey} after ${delay}ms`);
            await new Promise(resolve => setTimeout(resolve, delay));
          }
        }
      }

      throw lastError;
    };
  };
}

class ApiClient {
  @Retry(3, 1000)
  async fetchData(url: string): Promise<any> {
    const response = await fetch(url);
    if (!response.ok) throw new Error(`HTTP ${response.status}`);
    return response.json();
  }
}
```

## NestJS Decorators

NestJS makes heavy use of decorators for dependency injection and routing. It currently uses legacy experimental decorators but has announced plans to migrate to Stage 3.

```typescript
import { Controller, Get, Post, Body, Injectable, Inject } from '@nestjs/common';

@Injectable()
class UserService {
  findAll() {
    return [{ id: 1, name: 'Alice' }];
  }
}

@Controller('users')
class UserController {
  constructor(private userService: UserService) {}

  @Get()
  findAll() {
    return this.userService.findAll();
  }

  @Post()
  create(@Body() createUserDto: { name: string }) {
    return { id: 2, ...createUserDto };
  }
}
```

NestJS decorators form a layered system: `@Controller` defines route prefixes, `@Get` and `@Post` define HTTP method bindings, `@Body` extracts request body data, and `@Injectable` marks classes for the dependency injection container. Understanding how these decorators work under the hood helps you build custom decorators and troubleshoot issues.

## Best Practices

1. **Use decorator factories**: Makes decorators configurable and reusable across different contexts.
2. **Keep decorators focused**: Each decorator should do one thing and do it well, following the Single Responsibility Principle.
3. **Document decorator behavior**: Decorators can be non-obvious; always document what they do and any side effects.
4. **Use the new standard**: Stage 3 decorators are the future. Use them for new projects unless you depend on a framework that requires legacy decorators.
5. **Avoid deep nesting**: Too many decorators make code hard to follow. Three or fewer decorators per declaration is a good guideline.
6. **Test decorated code**: Ensure your tests cover both the decorated and undecorated behavior.
7. **Use TypeScript's type system**: Leverage generics and type constraints in your decorators to catch errors at compile time.

## Common Pitfalls

| Pitfall | Impact | Solution |
|---------|--------|----------|
| Mixing legacy and new | Compilation errors | Use one or the other per project |
| Decorator execution order | Unexpected behavior | Document and test order |
| this binding issues | Undefined context | Use arrow functions or bind |
| Over-decorating | Hard to understand | Keep decorators simple |
| Missing reflect-metadata | Runtime errors in legacy | Install polyfill for legacy decorators |
| Parameter decorators in Stage 3 | Not supported | Use alternative DI patterns |

## Testing Decorated Code

Testing code that uses decorators requires understanding how decorators affect the behavior of the decorated declarations. When testing a decorated method, you are testing both the original method and the decorator's behavior. Use dependency injection decorators to replace real services with mocks during testing. Create test-specific decorators that add debugging or assertion logic. When testing decorator composition, verify that the decorators apply in the correct order and that the combined behavior is correct. Use TypeScript's type checking to ensure that decorated declarations maintain their expected types, catching type errors that might be introduced by decorators at compile time.

```typescript
// Testing with decorator-aware mocking
class Calculator {
  @Log
  add(a: number, b: number): number {
    return a + b;
  }
}

describe('Calculator', () => {
  it('should add numbers correctly', () => {
    const calc = new Calculator();
    const result = calc.add(2, 3);
    expect(result).toBe(5);
  });

  it('should call the decorator wrapper', () => {
    const consoleSpy = jest.spyOn(console, 'log');
    const calc = new Calculator();
    calc.add(2, 3);
    expect(consoleSpy).toHaveBeenCalledWith('Calling add with args:', [2, 3]);
  });
});
```

## Performance Considerations

Decorators add a small runtime overhead because they wrap or modify declarations at class creation time. For most applications, this overhead is negligible. However, in performance-critical code paths where methods are called millions of times per second, the overhead of a logging or validation decorator can become measurable. Profile your application to determine whether decorator overhead is a bottleneck. If it is, consider removing decorators from hot code paths in production builds using conditional compilation or build-time decorator removal. Alternatively, implement lightweight decorators that do minimal work during the hot path and defer expensive operations like logging to a background queue.

```typescript
// Lightweight conditional decorator
function DevOnly(decorator: Function) {
  return process.env.NODE_ENV === 'development' ? decorator : (target: any) => target;
}

class Service {
  @DevOnly(Log)
  expensiveOperation() {
    // This method's logging overhead is removed in production
  }
}
```

## Decorator Patterns

Common decorator patterns include:

- **Before-after pattern**: Wraps a method to execute code before and after the original method (logging, profiling).
- **Memoization pattern**: Caches method results based on their arguments for expensive computations.
- **Throttle and debounce patterns**: Limits how frequently a method can be called, essential for UI event handlers.
- **Validation pattern**: Checks method arguments against a schema before execution.
- **Retry pattern**: Automatically retries a failed method call with exponential backoff for transient failures.
- **Circuit breaker pattern**: Prevents calls to a failing service after repeated failures, allowing it to recover.

These patterns can be combined using decorator composition to create sophisticated behavior from simple building blocks.

## Framework Integration

Modern TypeScript frameworks are adopting Stage 3 decorators. Angular uses decorators extensively for component definition, dependency injection, and lifecycle hooks. NestJS uses decorators for routing, middleware, and validation. TypeORM uses decorators for entity mapping and relationship definition. These frameworks are updating their decorator implementations to use the Stage 3 proposal, which provides a standardized foundation. When using decorators with frameworks, follow the framework's documentation for the correct decorator syntax and behavior. Be aware that some frameworks may still use legacy decorators during the transition period.

## Migration Guide

When migrating your codebase from legacy decorators to Stage 3 decorators, follow this systematic approach:

1. **Upgrade TypeScript** to 5.0+ to get Stage 3 support.
2. **Audit your decorators** — Identify all custom decorators and categorize them by type (class, method, property, parameter).
3. **Replace parameter decorators first** — Since Stage 3 does not support parameter decorators, you need alternative approaches like using metadata or factory patterns.
4. **Convert method decorators** — The new method decorator signature is straightforward. Replace `PropertyDescriptor` manipulation with return-value wrapping.
5. **Convert class decorators** — Update to use `ClassDecoratorContext` and return-value replacement pattern.
6. **Handle property decorators** — Migrate to `accessor` decorators or field decorators depending on the use case.
7. **Update framework dependencies** — Ensure your framework versions support Stage 3 decorators.
8. **Run comprehensive tests** — Verify that all decorated code behaves correctly after migration.

### Automated Migration Tools

For large codebases, automated codemods can handle the mechanical transformation:

```bash
# Using ts-migrate for automated migration
npx ts-migrate --path ./src --plugin decorator-migration
```

Manual review is necessary for complex decorator implementations that rely on legacy features like parameter decorators or `Reflect.metadata`.

## Conclusion

TypeScript decorators provide powerful metaprogramming capabilities. The legacy `experimentalDecorators` flag is widely used in frameworks like NestJS and Angular, while the new Stage 3 standard is the future. Understanding both approaches lets you work with existing code and adopt the new standard as it stabilizes.

Key takeaways:

1. **Legacy decorators** use `experimentalDecorators: true` and are used by NestJS/Angular. They support parameter decorators and have a different API.
2. **Stage 3 decorators** are the new ECMAScript standard with context objects, initializer return values, and auto-accessors. They do not support parameter decorators.
3. **Decorator factories** make decorators configurable and are the recommended pattern for both legacy and Stage 3.
4. **Common patterns** include logging, validation, memoization, dependency injection, access control, retry logic, and rate limiting.
5. **Migration is worthwhile** for new projects to align with the JavaScript standard, but existing framework-heavy codebases should wait for framework support before migrating.

The Stage 3 decorator specification represents the culmination of nearly a decade of refinement. As the JavaScript ecosystem continues to adopt these decorators, developers who understand both the legacy and new systems will be well-positioned to build sophisticated applications with clean, maintainable abstractions. Start experimenting with Stage 3 decorators in new projects today, and plan your migration strategy for existing codebases as framework support matures.
