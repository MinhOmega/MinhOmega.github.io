## Introduction

Change Data Capture (CDC) is the practice of detecting and capturing changes made to data in a database, then streaming those changes to downstream systems in real-time. Instead of polling the database for changes (which is inefficient and introduces latency), CDC leverages the database's own transaction log to capture every INSERT, UPDATE, and DELETE as it happens.

CDC is the backbone of modern event-driven architectures. It enables real-time data synchronization between systems, powers event sourcing patterns, feeds analytics pipelines without impacting production databases, and supports microservice communication through domain events. Companies like Netflix, Uber, and LinkedIn process billions of CDC events daily using tools like Debezium and Kafka Connect. This guide covers the patterns, tools, and implementation strategies for CDC in production.

## Understanding CDC: Core Concepts

### How CDC Works

CDC captures changes from the database's transaction log (WAL in PostgreSQL, binlog in MySQL, redo log in Oracle). This is the same mechanism used for replication—the CDC connector reads the log in the same way a standby replica would.

The key advantage of log-based CDC is that it has zero impact on the source database's performance. No triggers, no polling queries, no additional writes. The transaction log already exists; CDC just reads it.

### CDC Patterns

**Log-based CDC**: Reads the database transaction log. Pros: zero performance impact, captures all changes, includes before/after values. Cons: requires database configuration, connector must handle log format specifics.

**Query-based CDC**: Periodically queries the database for changes using timestamps or version columns. Pros: works with any database, no configuration needed. Cons: adds load to the database, misses deletes, introduces latency.

**Trigger-based CDC**: Database triggers capture changes to a shadow table. Pros: captures all changes, works with any database. Cons: adds write overhead, triggers are database-specific, hard to maintain.

### The Debezium Architecture

Debezium is the most popular CDC platform. It's built on Apache Kafka Connect and provides connectors for PostgreSQL, MySQL, MongoDB, Oracle, SQL Server, and more:

```
Source DB → Debezium Connector → Kafka → [Consumers]
                                         ├→ Elasticsearch
                                         ├→ Data Warehouse
                                         ├→ Microservice B
                                         └→ Analytics Pipeline
```

Debezium captures row-level changes and publishes them as events to Kafka topics. Each table gets its own topic, and each change is a message with before/after values, metadata (timestamp, operation type, source), and the complete row state.

## Architecture and Design Patterns

### The Event Streaming Pipeline

```
PostgreSQL (WAL) → Debezium → Kafka → Consumer Group
                                   ├→ Search Indexer (Elasticsearch)
                                   ├→ Cache Invalidator (Redis)
                                   ├→ Notification Service
                                   ├→ Data Warehouse (BigQuery)
                                   └→ Audit Log
```

### The Outbox Pattern

For microservices that need to publish domain events, the outbox pattern uses CDC to capture events written to an outbox table:

```
Service A → Write to outbox table → CDC captures → Kafka → Service B
```

This ensures atomicity—the domain event and the business transaction are written in the same database transaction, eliminating dual-write problems.

### The Event Sourcing Pattern

CDC can feed an event store that maintains a complete history of every change:

```
Source DB → CDC → Event Store → Projections (read models)
```

Each event represents a state change. Projections rebuild the current state by replaying events.

### Kafka Consumer for CDC Events

```typescript
import { Kafka, Consumer } from "kafkajs";

const kafka = new Kafka({
  clientId: "cdc-consumer",
  brokers: ["kafka1:9092", "kafka2:9092"],
});

interface CDCEvent {
  before: Record<string, any> | null;
  after: Record<string, any> | null;
  op: "c" | "u" | "d" | "r"; // create, update, delete, read
  source: {
    table: string;
    ts_ms: number;
  };
}

async function consumeCDC() {
  const consumer = kafka.consumer({ groupId: "data-sync-group" });
  await consumer.connect();
  await consumer.subscribe({ topic: "cdc.public.users", fromBeginning: false });

  await consumer.run({
    eachMessage: async ({ topic, partition, message }) => {
      const event: CDCEvent = JSON.parse(message.value!.toString());

      switch (event.op) {
        case "c": // Create
          await handleCreate(event.after!);
          break;
        case "u": // Update
          await handleUpdate(event.before!, event.after!);
          break;
        case "d": // Delete
          await handleDelete(event.before!);
          break;
      }
    },
  });
}

async function handleCreate(record: Record<string, any>) {
  // Index in Elasticsearch
  await elasticsearch.index({
    index: "users",
    id: record.id.toString(),
    body: record,
  });
}

async function handleUpdate(before: Record<string, any>, after: Record<string, any>) {
  // Invalidate cache
  await redis.del(`user:${after.id}`);

  // Update search index
  await elasticsearch.update({
    index: "users",
    id: after.id.toString(),
    body: { doc: after },
  });
}

async function handleDelete(record: Record<string, any>) {
  await elasticsearch.delete({ index: "users", id: record.id.toString() });
  await redis.del(`user:${record.id}`);
}
```

### The Outbox Pattern Implementation

```typescript
// Service writes to outbox in same transaction
async function createUser(data: CreateUserInput) {
  return db.transaction(async (trx) => {
    // Create user
    const [user] = await trx("users").insert(data).returning("*");

    // Write domain event to outbox (same transaction)
    await trx("outbox").insert({
      aggregate_type: "User",
      aggregate_id: user.id,
      event_type: "UserCreated",
      payload: JSON.stringify({
        userId: user.id,
        email: user.email,
        name: user.name,
        occurredAt: new Date().toISOString(),
      }),
    });

    return user;
  });
  // CDC captures the outbox insert and publishes to Kafka
}
```

## Real-World Use Cases

### Real-Time Search Index Sync

An e-commerce platform used CDC to sync product data from PostgreSQL to Elasticsearch. When a product's price or availability changed, the CDC event triggered an Elasticsearch update within seconds. Before CDC, the search index was refreshed every 15 minutes, leading to stale results and customer complaints.

### Cross-Service Data Synchronization

A microservices architecture used CDC to keep read models in sync across services. The Order Service published CDC events when orders changed, and the Analytics Service consumed these events to update its data warehouse. This eliminated the need for complex API calls between services.

### Audit Logging

A financial services company used CDC to capture every data change for regulatory compliance. Every INSERT, UPDATE, and DELETE was captured with before/after values and stored in an immutable audit log. CDC provided complete auditability without modifying application code.

### Cache Invalidation

A social media platform used CDC to invalidate Redis caches when underlying data changed. When a user updated their profile, the CDC event triggered cache invalidation, ensuring other users saw the updated profile immediately.

## Best Practices for Production

1. **Use logical replication, not triggers** — Log-based CDC has zero performance impact on the source database. Trigger-based CDC adds write latency and maintenance burden.

2. **Monitor replication lag** — CDC connectors can fall behind if the consumer is slow. Alert on lag exceeding your latency requirements.

3. **Handle schema evolution** — Database schema changes (column additions, renames) must be handled gracefully. Use a schema registry (Confluent Schema Registry) to manage schema versions.

4. **Implement idempotent consumers** — CDC events may be delivered more than once. Consumers must handle duplicates without side effects.

5. **Use the outbox pattern for microservices** — Don't rely on CDC directly from business tables. Write domain events to an outbox table and capture them with CDC.

6. **Monitor connector health** — Debezium connectors can fail due to network issues, database restarts, or schema changes. Monitor connector status and restart automatically.

7. **Set appropriate retention** — Kafka topic retention should match your replay requirements. If you need to reprocess events, ensure retention is long enough.

8. **Test with production data volumes** — CDC performance under load may differ from development. Test with realistic data volumes and change rates.

## Common Pitfalls and Solutions

| Pitfall | Impact | Solution |
|---------|--------|----------|
| Replication slot grows unbounded | Disk fills up, database stops | Monitor slot lag, drop unused slots |
| Schema changes break connector | CDC stops working | Use schema registry, test schema changes |
| Duplicate events | Data inconsistency | Implement idempotent consumers |
| Missing DELETE events | Stale data in downstream | Configure tombstone events |
| High-volume tables overwhelm Kafka | Consumer lag, dropped events | Partition by table, scale consumers |
| Initial snapshot blocks production | Performance impact | Snapshot during low-traffic windows |

## Advanced Patterns

### CDC-Based Event Sourcing

```typescript
class EventStore {
  async append(event: DomainEvent): Promise<void> {
    await this.db("events").insert({
      aggregate_id: event.aggregateId,
      aggregate_type: event.aggregateType,
      event_type: event.eventType,
      data: JSON.stringify(event.data),
      version: event.version,
      created_at: new Date(),
    });
    // CDC captures this insert and publishes to Kafka
  }

  async getEvents(aggregateId: string): Promise<DomainEvent[]> {
    return this.db("events")
      .where({ aggregate_id: aggregateId })
      .orderBy("version", "asc");
  }
}
```

### Multi-Region CDC

```
Region A DB → Debezium → Kafka A → MirrorMaker → Kafka B → Region B consumers
```

Kafka MirrorMaker replicates CDC events across regions, enabling near-real-time data synchronization between geographically distributed databases.

```typescript

describe("CDC Pipeline", () => {

    // Insert into source database
    await db("users").insert({ name: "Test User", email: "test@example.com" });

    // Consume CDC event
    const event = await consumeNextEvent("cdc.public.users");

    expect(event.op).toBe("c");
    expect(event.after.name).toBe("Test User");
    expect(event.after.email).toBe("test@example.com");
  });

  it("captures DELETE with before state", async () => {
    const [user] = await db("users").insert({ name: "Delete Me" }).returning("*");
    await db("users").where({ id: user.id }).delete();

    const event = await consumeNextEvent("cdc.public.users");

    expect(event.op).toBe("d");
    expect(event.before.id).toBe(user.id);
  });
});
```

## Future Outlook

CDC is evolving toward serverless and fully managed offerings. Confluent's fully managed Debezium connectors, AWS DMS (Database Migration Service), and Google Cloud's Datastream are making CDC accessible without managing Kafka clusters.

The emergence of standards like CloudEvents is providing a common event format across CDC tools, making it easier to switch between implementations. Combined with the growth of event-driven architectures, CDC is becoming a foundational infrastructure component for modern data platforms.

Implementing CDC patterns requires careful consideration of ordering guarantees, exactly-once delivery, and schema evolution to maintain data consistency across systems.

## Conclusion

CDC is the bridge between your database and the rest of your architecture. The key takeaways:

1. **Log-based CDC has zero performance impact** — Read the transaction log, don't poll the database
2. **Debezium + Kafka is the standard** — Mature, well-documented, supports all major databases
3. **The outbox pattern solves dual-write problems** — Write domain events in the same transaction as business data
4. **Idempotent consumers are essential** — CDC events may be delivered more than once
5. **Monitor replication lag** — CDC is only useful if it keeps up with the rate of change

Start by enabling logical replication on your PostgreSQL database and deploying a single Debezium connector for one table. Observe the events flowing through Kafka. Once you see the pattern, expanding to additional tables and consumers is straightforward.
