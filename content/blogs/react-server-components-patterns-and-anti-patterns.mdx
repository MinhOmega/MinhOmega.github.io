## Introduction

React Server Components (RSC) introduce a new dimension to React development: the server/client boundary. Every component is a Server Component by default—running only on the server, with zero client JavaScript. Components marked with `'use client'` become Client Components that ship to the browser and can use hooks, browser APIs, and event handlers. This boundary is not just a technical detail; it determines where your code runs, what data it can access, and how much JavaScript reaches the user's browser.

With this new model comes a new set of patterns and anti-patterns. The patterns that work in traditional React (client-side data fetching, prop drilling through context, large client bundles) become anti-patterns in RSC. Meanwhile, patterns that were previously impossible or awkward (direct database access in components, streaming partial HTML, zero-JS static content) become the foundation of good architecture. Understanding these patterns is essential for building performant RSC applications.

This guide catalogs the most important RSC patterns and anti-patterns, organized by category: data fetching, component composition, state management, caching, and performance. Each pattern includes code examples showing the correct approach and the anti-pattern it replaces. By the end, you will have a clear mental model for designing RSC applications that are fast, maintainable, and leverage the full power of the server/client model.

## Understanding RSC Patterns: Core Concepts

### The Golden Rule

Server Components are the default. Client Components are the exception. Every `'use client'` directive should be justified by a genuine need for interactivity, browser APIs, or React state. If a component can run on the server, it should.

### The Serialization Boundary

Data passed from Server to Client Components must be serializable (like JSON). Functions, class instances, symbols, and non-serializable values cannot cross. This constraint shapes how you compose components.

## Patterns and Anti-Patterns

### Pattern 1: Server Component as Data Fetcher

**Pattern**: Fetch data directly in Server Components using `async/await`.

```tsx
// ✅ CORRECT: Server Component fetches its own data
async function ProductList() {
  const products = await db.products.findMany({ take: 20 });
  return (
    <div>
      {products.map(p => <ProductCard key={p.id} product={p} />)}
    </div>
  );
}
```

**Anti-Pattern**: Fetching data in Client Components with `useEffect`.

```tsx
// ❌ ANTI-PATTERN: Client-side data fetching
'use client';
function ProductList() {
  const [products, setProducts] = useState([]);
  useEffect(() => {
    fetch('/api/products').then(r => r.json()).then(setProducts);
  }, []);
  // Waterfall: JS loads → component mounts → fetch starts → data arrives → render
}
```

### Pattern 2: Composition Over Props

**Pattern**: Use children and composition to pass non-serializable values.

```tsx
// ✅ CORRECT: Client Component wraps Server Component via children
// app/page.tsx (Server Component)
async function Page() {
  const data = await fetchData();
  return (
    <InteractiveWrapper>
      <StaticContent data={data} />
    </InteractiveWrapper>
  );
}

// app/interactive-wrapper.tsx (Client Component)
'use client';
function InteractiveWrapper({ children }) {
  const [isOpen, setIsOpen] = useState(false);
  return (
    <div onClick={() => setIsOpen(!isOpen)}>
      {children}
      {isOpen && <Details />}
    </div>
  );
}
```

**Anti-Pattern**: Passing functions across the boundary.

```tsx
// ❌ ANTI-PATTERN: Passing non-serializable props
async function Page() {
  const handler = () => console.log('clicked'); // Function!
  return <ClientButton onClick={handler} />; // Serialization error
}
```

### Pattern 3: Push Client Boundaries Down

**Pattern**: Keep `'use client'` at the leaf level.

```tsx
// ✅ CORRECT: Only the interactive leaf is a Client Component
// app/product/page.tsx (Server Component)
async function ProductPage({ params }) {
  const product = await db.products.findUnique({ where: { id: params.id } });
  return (
    <div>
      <h1>{product.name}</h1>
      <p>{product.description}</p>
      <PriceDisplay price={product.price} />
      <AddToCartButton productId={product.id} />
    </div>
  );
}

// app/add-to-cart-button.tsx (Client Component - leaf)
'use client';
function AddToCartButton({ productId }) {
  const [loading, setLoading] = useState(false);
  return <button onClick={() => addToCart(productId)}>Add to Cart</button>;
}
```

**Anti-PATTERN**: Marking entire pages as client components.

```tsx
// ❌ ANTI-PATTERN: Entire page is a Client Component
'use client';
function ProductPage() {
  // All data fetching, state, and rendering ships to client
  // Much more JavaScript, slower hydration
}
```

### Pattern 4: Server-Side Data Transformation

**Pattern**: Transform and filter data on the server before sending to client.

```tsx
// ✅ CORRECT: Server filters and transforms
async function Dashboard() {
  const rawData = await fetchExpensiveData();
  const summary = {
    total: rawData.length,
    average: rawData.reduce((a, b) => a + b.value, 0) / rawData.length,
    topItems: rawData.sort((a, b) => b.value - a.value).slice(0, 10),
  };
  return <DashboardCharts summary={summary} />; // Only summary crosses boundary
}
```

**Anti-Pattern**: Sending raw data to client for transformation.

```tsx
// ❌ ANTI-PATTERN: Client transforms large datasets
'use client';
function Dashboard({ rawData }) { // 10,000 items serialized and sent to client
  const summary = useMemo(() => expensiveTransform(rawData), [rawData]);
  return <Chart data={summary} />;
}
```

### Pattern 5: Streaming with Suspense

**Pattern**: Use Suspense boundaries to stream content progressively.

```tsx
// ✅ CORRECT: Fast content renders immediately, slow content streams in
async function Page() {
  return (
    <div>
      <Header /> {/* Immediate */}
      <Suspense fallback={<ArticleSkeleton />}>
        <Article /> {/* Streams when ready */}
      </Suspense>
      <Suspense fallback={<CommentsSkeleton />}>
        <Comments /> {/* Streams independently */}
      </Suspense>
    </div>
  );
}
```

**Anti-Pattern**: No Suspense boundaries—entire page waits for slowest data.

```tsx
// ❌ ANTI-PATTERN: Everything blocked by slowest fetch
async function Page() {
  const [article, comments] = await Promise.all([
    fetchArticle(), // Fast
    fetchComments(), // Slow
  ]);
  // Nothing renders until both complete
  return <div><Article data={article} /><Comments data={comments} /></div>;
}
```

### Pattern 6: Server Actions for Mutations

```tsx
// ✅ CORRECT: Server Action with validation and revalidation
'use server';
async function addTodo(formData: FormData) {
  const title = formData.get('title');
  if (!title || title.length < 3) return { error: 'Too short' };
  await db.todos.create({ data: { title } });
  revalidatePath('/todos');
  return { success: true };
}
```

### Pattern 7: Caching with revalidateTag

```tsx
// ✅ CORRECT: Tag-based cache invalidation
async function getProduct(id: string) {
  const product = await fetch(`/api/products/${id}`, {
    next: { tags: [`product-${id}`] },
  });
  return product.json();
}

// Invalidate specific product
'use server';
async function updateProduct(id: string, data: ProductData) {
  await db.products.update({ where: { id }, data });
  revalidateTag(`product-${id}`);
}
```

## Real-World Use Cases

### Use Case 1: Blog with Interactive Comments

Server Components render the blog post (zero JS). A Client Component handles the comment form with state management and optimistic updates.

### Use Case 2: E-Commerce Catalog

Server Components render product listings and details. Client Components handle cart management, quantity selectors, and image galleries.

### Use Case 3: Dashboard with Real-Time Widgets

Server Components render the dashboard layout and static widgets. Client Components handle WebSocket-connected real-time widgets and interactive charts.

## Best Practices for Production

1. **Default to Server Components**: Every component starts as a Server Component. Only add `'use client'` when you need interactivity.
2. **Use composition to pass non-serializable values**: Wrap Client Components around Server Components via children, not props.
3. **Fetch data in Server Components**: Eliminate `useEffect` data fetching patterns entirely.
4. **Transform data on the server**: Don't send raw data to the client. Filter, sort, and aggregate on the server.
5. **Use Suspense for streaming**: Wrap slow components in Suspense boundaries to avoid blocking the entire page.
6. **Cache with tags**: Use `revalidateTag` for targeted cache invalidation instead of `revalidatePath` for broader invalidation.
7. **Analyze client bundles**: Regularly check how much JavaScript you're shipping. Tools like `@next/bundle-analyzer` reveal client component bloat.
8. **Test the boundary**: Verify that Server Components don't accidentally import client-only code and vice versa.

## Common Pitfalls and Solutions

| Pitfall | Impact | Solution |
|---------|--------|----------|
| `'use client'` too high | Large JS bundle | Push boundary to leaf components |
| Passing functions as props | Serialization error | Use composition (children pattern) |
| Client-side data fetching | Waterfalls, slower page | Fetch in Server Components |
| No Suspense boundaries | Slow first paint | Add Suspense around slow components |
| Sending large datasets to client | Slow serialization, large payload | Transform on server, send summary |
| Using hooks in Server Components | Runtime error | Move to Client Component |
| Not caching server data | Redundant database queries | Use `unstable_cache` or fetch caching |

## Performance Optimization

```tsx
// Use React.cache() for request-level deduplication
import { cache } from 'react';

const getUser = cache(async (id: string) => {
  return db.users.findUnique({ where: { id } });
});

// Multiple components calling getUser(id) → one DB query per request

// Parallel data fetching in Server Components
async function Dashboard() {
  const [user, orders, analytics] = await Promise.all([
    getUser('123'),
    getOrders('123'),
    getAnalytics(),
  ]);
  // All three fetch in parallel, not sequentially
}
```

## Future Outlook

RSC patterns are still evolving. The React team is working on improving the server-client boundary tooling, adding better error messages for serialization issues, and optimizing the wire format. As the ecosystem matures, we can expect more libraries to provide Server Component-compatible APIs and better developer tools for understanding the boundary.

## Conclusion

React Server Components introduce a new way of thinking about React architecture. The patterns are: fetch data in Server Components, use composition to pass non-serializable values, push client boundaries to leaves, transform data on the server, stream with Suspense, and cache with tags. The anti-patterns are: marking everything as `'use client'`, fetching data in Client Components, passing functions across the boundary, and sending large raw datasets to the client.

By following these patterns, you build applications that ship minimal JavaScript, load fast, and provide excellent user experiences. The server/client boundary is not a limitation—it is a design tool that forces clean separation between data access (server) and interactivity (client).
