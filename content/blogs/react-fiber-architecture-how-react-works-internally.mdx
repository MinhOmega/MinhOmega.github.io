## Introduction

React Fiber is the reconciliation engine that powers React 16 and beyond. It's the complete rewrite of React's core algorithm that enables features like concurrent rendering, Suspense, and priority-based updates. Understanding Fiber isn't just academic — it explains why React behaves the way it does, why certain patterns are faster than others, and how to write components that leverage React's scheduling capabilities.

Before Fiber, React used a recursive reconciliation algorithm that couldn't pause, abort, or prioritize work. Once rendering started, it had to complete synchronously. Fiber changed this by introducing a linked-list tree structure that allows React to pause work, resume it later, and abandon low-priority updates when higher-priority ones arrive.

## The Problem Fiber Solves

### Pre-Fiber Reconciliation

In React 15 and earlier, reconciliation was a recursive process:

```typescript
// Simplified pre-Fiber reconciliation
function reconcileChildren(element) {
  // This runs recursively — cannot be interrupted
  const children = element.props.children;
  for (const child of children) {
    updateDOM(child);       // Block until done
    reconcileChildren(child); // Then recurse into children
  }
}
```

This approach has a critical limitation: if the component tree is large, reconciliation blocks the main thread for potentially hundreds of milliseconds. During this time, the browser can't respond to user input — clicks, scrolls, and animations freeze.

### The 16ms Budget

Browsers render at 60fps, meaning each frame has a 16ms budget. If JavaScript runs for longer than 16ms, frames are dropped and the UI feels janky. With large component trees, React's recursive reconciliation could easily exceed this budget.

## Fiber's Solution: Incremental Rendering

Fiber breaks rendering into small units of work that can be started, paused, and resumed:

```typescript
// Fiber work loop (simplified)
function workLoop(deadline) {
  while (nextUnitOfWork && !shouldYield()) {
    nextUnitOfWork = performUnitOfWork(nextUnitOfWork);
  }

  if (nextUnitOfWork) {
    // Not done — schedule continuation
    requestIdleCallback(workLoop);
  } else {
    // All work done — commit to DOM
    commitRoot();
  }
}
```

The key insight: React can yield control back to the browser between units of work, allowing the browser to handle high-priority tasks (user input, animations) before React resumes rendering.

## The Fiber Node Structure

Each React element has a corresponding Fiber node. Fiber nodes form a linked-list tree:

```typescript
interface Fiber {
  // Identity
  type: string | Function | null;
  key: string | null;

  // Tree structure (linked list)
  child: Fiber | null;    // First child
  sibling: Fiber | null;  // Next sibling
  return: Fiber | null;   // Parent fiber
  index: number;

  // State
  pendingProps: any;
  memoizedState: any;
  memoizedProps: any;

  // Effects
  effectTag: number;       // Placement, Update, Deletion
  nextEffect: Fiber | null;
  firstEffect: Fiber | null;
  lastEffect: Fiber | null;

  // Work
  expirationTime: number;
  mode: number;
  lanes: number;

  // Alternates
  alternate: Fiber | null; // Double buffering
}
```

### The Linked-List Tree

Unlike the recursive tree structure, Fiber uses a linked-list traversal:

```typescript
// Traditional tree (recursive)
//        A
//       / \
//      B   C
//     / \   \
//    D   E   F

// Fiber linked-list traversal
// A → child → B → child → D → sibling → E → return → B → sibling → C → child → F
//
// Traversal order: A, B, D, E, C, F
// Always: visit child first, then sibling, then return to parent
```

This structure allows React to pause at any node, save its position, and resume later — something impossible with the recursive approach.

## The Two Phases

### Render Phase (Interruptible)

The render phase creates new Fiber nodes, compares them with previous nodes, and determines what changes need to happen. This phase is pure — it doesn't modify the DOM:

```typescript
function performUnitOfWork(fiber: Fiber): Fiber | null {
  // 1. Process this fiber
  const Component = fiber.type;
  if (typeof Component === 'function') {
    // Function component — call it
    const children = Component(fiber.pendingProps);
    reconcileChildren(fiber, children);
  } else {
    // Host component (div, span, etc.) — reconcile children
    reconcileChildren(fiber, fiber.pendingProps.children);
  }

  // 2. Return next unit of work
  if (fiber.child) return fiber.child;

  let next = fiber;
  while (next) {
    if (next.sibling) return next.sibling;
    next = next.return;
  }

  return null; // No more work
}
```

### Commit Phase (Synchronous)

The commit phase applies all changes to the DOM. This phase is synchronous and cannot be interrupted — partial updates would create inconsistent UI:

```typescript
function commitRoot() {
  // 1. Commit mutations
  commitWork(rootFiber.firstEffect);

  // 2. Run lifecycle effects
  // componentDidMount, componentDidUpdate, useEffect callbacks
}

function commitWork(fiber: Fiber | null) {
  while (fiber) {
    switch (fiber.effectTag) {
      case PLACEMENT:
        fiber.stateNode.appendChild(fiber.child?.stateNode);
        break;
      case UPDATE:
        updateDOMProperties(fiber.stateNode, fiber.memoizedProps, fiber.pendingProps);
        break;
      case DELETION:
        fiber.return?.stateNode.removeChild(fiber.stateNode);
        break;
    }
    fiber = fiber.nextEffect;
  }
}
```

## Double Buffering

React maintains two trees: the **current** tree (what's on screen) and the **work-in-progress** tree (what's being built). This is similar to double buffering in graphics:

```typescript
// When a component updates:
function createWorkInProgress(current: Fiber, pendingProps: any): Fiber {
  let workInProgress = current.alternate;

  if (!workInProgress) {
    // First render — create new fiber
    workInProgress = new Fiber(current.type, pendingProps);
    workInProgress.alternate = current;
    current.alternate = workInProgress;
  } else {
    // Reuse fiber from previous render
    workInProgress.pendingProps = pendingProps;
    workInProgress.effectTag = UPDATE;
  }

  return workInProgress;
}
```

When the commit phase completes, React swaps the trees: the work-in-progress becomes the current tree, and the old current tree becomes the next work-in-progress.

## Priority Scheduling with Lanes

React 18 introduced the Lanes model for priority scheduling. Different updates have different priorities:

```typescript
// Priority levels (simplified)
const SyncLane = 0b0000000000000000000000000000001;
const InputContinuousLane = 0b0000000000000000000000000000100;
const DefaultLane = 0b0000000000000000000000000010000;
const TransitionLane = 0b0000000000000000000000010000000;
const IdleLane = 0b0100000000000000000000000000000;
```

Higher-priority updates can interrupt lower-priority work:

```typescript
// User input — high priority, cannot be deferred
function handleInput(value) {
  startTransition(() => {
    setInputValue(value); // SyncLane — processes immediately
  });
}

// Filter results — lower priority, can be deferred
function handleFilter(filter) {
  startTransition(() => {
    setFilter(filter); // TransitionLane — can be interrupted
  });
}
```

## How useEffect Works in Fiber

Fiber nodes track effects using a linked list:

```typescript
// When useEffect is called during render:
function useEffect(callback, deps) {
  const fiber = getCurrentFiber();

  const effect = {
    tag: PassiveEffect,  // useEffect
    create: callback,
    deps: deps,
    destroy: null,
  };

  // Add to fiber's effect list
  if (!fiber.updateQueue) {
    fiber.updateQueue = { lastEffect: effect };
    effect.next = effect; // Circular linked list
  } else {
    const lastEffect = fiber.updateQueue.lastEffect;
    effect.next = lastEffect.next;
    lastEffect.next = effect;
    fiber.updateQueue.lastEffect = effect;
  }
}
```

During the commit phase, React processes these effects:

```typescript
function commitPassiveEffects(fiber: Fiber) {
  const updateQueue = fiber.updateQueue;
  if (!updateQueue) return;

  let effect = updateQueue.lastEffect.next; // Start of circular list

  do {
    if (effect.tag === PassiveEffect) {
      // Run cleanup from previous render
      if (effect.destroy) {
        effect.destroy();
      }
      // Run new effect
      effect.destroy = effect.create();
    }
    effect = effect.next;
  } while (effect !== updateQueue.lastEffect.next);
}
```

## Concurrent Features Enabled by Fiber

### Suspense

Suspense works by allowing a component to "suspend" — telling React to skip it and come back later:

```typescript
function SuspenseBoundary({ children, fallback }) {
  try {
    return children;
  } catch (promise) {
    if (promise instanceof Promise) {
      // Component suspended — show fallback
      promise.then(() => {
        // Data ready — re-render
        scheduleUpdate(fiber);
      });
      return fallback;
    }
    throw promise; // Re-throw non-promise errors
  }
}
```

### useTransition

```typescript
function SearchPage() {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState([]);
  const [isPending, startTransition] = useTransition();

  function handleChange(e) {
    // Urgent: update input immediately
    setQuery(e.target.value);

    // Transition: can be deferred
    startTransition(() => {
      setResults(filterResults(e.target.value));
    });
  }

  return (
    <div>
      <input value={query} onChange={handleChange} />
      {isPending ? <Spinner /> : <ResultList results={results} />}
    </div>
  );
}
```

### useDeferredValue

```typescript
function SearchResults({ query }) {
  const deferredQuery = useDeferredValue(query);
  const isStale = query !== deferredQuery;

  return (
    <div style={{ opacity: isStale ? 0.7 : 1 }}>
      <ExpensiveList query={deferredQuery} />
    </div>
  );
}
```

## Practical Implications

### Why Keys Matter

Fiber uses keys to match old and new children:

```typescript
// Without keys — React re-renders all items
<ul>
  {items.map((item, i) => <li key={i}>{item.name}</li>)}
</ul>

// With stable keys — React reuses and moves items
<ul>
  {items.map(item => <li key={item.id}>{item.name}</li>)}
</ul>
```

### Why Functional Updates Matter

```typescript
// BAD: Stale closure
setCount(count + 1); // Uses count from render closure

// GOOD: Functional update
setCount(prev => prev + 1); // Always uses latest value
```

With concurrent rendering, the `count` variable might be stale by the time the update processes. Functional updates always use the latest state.

### Why Batching Matters

React 18 automatically batches all state updates:

```typescript
function handleClick() {
  // Before React 18: two re-renders
  // React 18: one re-render
  setA(1);
  setB(2);
}
```

Fiber makes this possible because updates are queued as lanes and processed together.

## Best Practices

1. **Use stable keys** — Help Fiber efficiently match and reuse nodes
2. **Use functional updates** — Avoid stale closures in concurrent mode
3. **Use `startTransition`** — Mark non-urgent updates for deferred processing
4. **Keep components pure** — Side effects in render phase cause bugs
5. **Avoid large component trees** — Even with Fiber, large trees are expensive
6. **Use `React.memo` wisely** — Prevent unnecessary re-renders of expensive components

## Common Pitfalls

| Pitfall | Impact | Solution |
|---------|--------|----------|
| Index as key | Poor list performance | Use stable unique IDs |
| Side effects in render | Unpredictable behavior | Use useEffect |
| Stale closures | Wrong values in concurrent mode | Use functional updates |
| Large component trees | Slow reconciliation | Split into smaller components |
| Mutating state directly | Skips re-render | Use setState or state setter |

### Render Phase and Commit Phase

React's rendering process is divided into two distinct phases that have very different characteristics and implications for application performance. The render phase is where React calls component functions, compares the results with the previous virtual DOM tree, and determines what changes need to be made. This phase is pure and side-effect free, meaning it can be interrupted, restarted, or discarded without any visible impact on the user interface. React can work on the render phase asynchronously, yielding control back to the browser between processing individual components to ensure that high-priority updates like user input are handled promptly. The commit phase is where React applies the calculated changes to the actual DOM. This phase must be synchronous and cannot be interrupted because partial updates to the real DOM would create visual inconsistencies that users could observe. Understanding this two-phase architecture helps developers write components that work well with React's scheduling system and avoid patterns that force synchronous rendering.

### Concurrent Features and Suspense

The concurrent rendering capabilities enabled by the Fiber architecture represent a fundamental shift in how React handles updates and asynchronous operations. Concurrent features allow React to prepare multiple versions of the user interface simultaneously, switching between them based on priority and user interaction. This capability enables patterns like automatic batching of state updates, transition APIs that keep the current interface responsive while preparing new content, and Suspense boundaries that provide elegant loading states for asynchronous operations. Developers who understand the underlying Fiber mechanics can leverage these concurrent features more effectively, building applications that feel faster and more responsive even when performing complex operations like data fetching, code splitting, and heavy computations.

## React DevTools and Fiber

The React DevTools Profiler is built on top of the Fiber architecture. When you profile a React application, DevTools hooks into Fiber's commit phase to record timing information for each component:

```javascript
// What DevTools records during profiling:
{
  componentName: "UserProfile",
  duration: 4.2,      // Time in ms for this component's render phase
  startTime: 1234.5,  // When rendering began
  commitTime: 1240.1, // When commit phase reached this component
  phases: {
    "render": 3.1,    // Time spent in render phase
    "commit": 1.1,    // Time spent in commit phase
  }
}
```

The Profiler's flamegraph view shows the component tree as Fiber sees it — each bar represents a Fiber node, and the width represents how long that node took to render. The ranked chart sorts components by render time, helping you identify the most expensive components. Understanding Fiber's two-phase architecture helps you interpret these profiles correctly: a long render phase suggests expensive component logic, while a long commit phase suggests expensive DOM mutations.

### Why Components Re-render

Understanding Fiber explains why certain patterns trigger unnecessary re-renders. When a parent Fiber node receives new props during reconciliation, React creates a new work-in-progress Fiber for it. If the component returns the same element structure with the same props, React can skip re-rendering children — but only if `React.memo` or the component's comparison logic says the props haven't changed. Without memoization, React traverses the entire subtree even if nothing changed:

```typescript
// This component re-renders whenever Parent re-renders
function ExpensiveChild({ data }) {
  return <div>{heavyComputation(data)}</div>;
}

// This component only re-renders when data actually changes
const ExpensiveChild = React.memo(function ExpensiveChild({ data }) {
  return <div>{heavyComputation(data)}</div>;
});
```

The React Compiler (React Forget), announced alongside React 19, aims to automate this memoization. It analyzes component code at build time and inserts memoization where it's safe to do so, eliminating the need for manual `React.memo`, `useMemo`, and `useCallback` calls. This works because the compiler understands Fiber's reconciliation rules and can determine when a component's output is guaranteed to be the same for the same inputs.

## Performance Optimization Patterns

### Avoiding Fiber Tree Thrashing

Certain patterns force React to do more work in the Fiber tree than necessary. Changing a component's position in the tree causes React to unmount the old Fiber and mount a new one, which destroys all state and DOM nodes:

```typescript
// BAD: Conditional rendering changes tree structure
function Page({ isLoggedIn }) {
  if (isLoggedIn) {
    return <Dashboard />;
  }
  return <Login />;
}
// Switching between these unmounts one and mounts the other

// BETTER: Same component, conditional content
function Page({ isLoggedIn }) {
  return isLoggedIn ? <DashboardContent /> : <LoginContent />;
}
// Both are always mounted, only content changes
```

### Fragment Keys in Lists

When rendering lists with multiple elements per item, use Fragment with a key to help Fiber match items correctly:

```typescript
// BAD: Each <li> gets a separate key, Fiber can't group them
items.map(item => [
  <li key={`${item.id}-name`}>{item.name}</li>,
  <li key={`${item.id}-value`}>{item.value}</li>,
]);

// GOOD: Fragment groups the elements with a single key
items.map(item => (
  <Fragment key={item.id}>
    <li>{item.name}</li>
    <li>{item.value}</li>
  </Fragment>
));
```

### Lazy Loading with Suspense

Fiber's ability to pause rendering enables code splitting with Suspense. When a lazy component hasn't loaded yet, Fiber suspends that subtree and renders the fallback:

```typescript
const HeavyChart = React.lazy(() => import('./HeavyChart'));

function Dashboard() {
  return (
    <Suspense fallback={<ChartSkeleton />}>
      <HeavyChart data={chartData} />
    </Suspense>
  );
}
```

When `HeavyChart` finishes loading, Fiber resumes rendering that subtree without re-rendering the rest of the Dashboard. This is only possible because Fiber can pause and resume work at any node in the tree.

## React 19 and the Future of Fiber

React 19 builds on the Fiber architecture with several enhancements that further leverage its capabilities. The React Compiler (formerly React Forget) automatically memoizes components and hooks, reducing the need for manual `useMemo` and `useCallback` calls. This works by analyzing component code during compilation and inserting memoization where the Fiber architecture would benefit from it.

Server Components integrate with Fiber by allowing components to render on the server and stream their results to the client. The Fiber tree on the client receives these pre-rendered components and incorporates them without re-executing the render phase. This reduces the amount of JavaScript sent to the browser and improves initial page load performance.

The `use()` hook in React 19 is a new primitive that works with Fiber's suspense mechanism. Unlike `useEffect` or `useMemo`, `use()` can be called conditionally and during rendering, allowing components to suspend based on promises or context values without wrapping in `Suspense` boundaries at every level:

```typescript
// React 19 use() hook
function UserProfile({ userId }) {
  const user = use(fetchUser(userId)); // Suspends if promise is pending
  const theme = use(ThemeContext);      // Reads context during render

  return (
    <div style={{ color: theme.primary }}>
      <h1>{user.name}</h1>
      <p>{user.email}</p>
    </div>
  );
}
```

React 19 also introduces Actions — functions that handle form submissions and async transitions natively. Actions integrate with Fiber's lane system to provide automatic pending states, error handling, and optimistic updates:

```typescript
// React 19 Actions
function UpdateName() {
  const [error, action, isPending] = useActionState(async (prev, formData) => {
    const newName = formData.get('name');
    const error = await updateName(newName);
    if (error) return error;
    redirect('/profile');
    return null;
  }, null);

  return (
    <form action={action}>
      <input type="text" name="name" />
      <button disabled={isPending}>{isPending ? 'Updating...' : 'Update'}</button>
      {error && <p>{error}</p>}
    </form>
  );
}
```

These additions demonstrate that Fiber's architecture continues to evolve, enabling new patterns that improve developer experience and application performance.

## Debugging Fiber

Understanding Fiber internals helps when debugging performance issues. React DevTools Profiler visualizes the render phase, showing which components rendered and how long each took:

```typescript
// Measure render performance with Profiler API
import { Profiler } from 'react';

function onRenderCallback(id, phase, actualDuration, baseDuration, startTime, commitTime) {
  console.log(`Component ${id} ${phase}: ${actualDuration}ms (base: ${baseDuration}ms)`);
  // actualDuration: time spent rendering this update
  // baseDuration: estimated time for full re-render without memoization
}

function App() {
  return (
    <Profiler id="App" onRender={onRenderCallback}>
      <Dashboard />
    </Profiler>
  );
}
```

When components render unexpectedly, check for missing keys in lists causing full re-renders, object or array literals in JSX props creating new references each render, context value changes propagating to all consumers, and state updates in render causing infinite loops. Use `React.StrictMode` in development to detect side effects in the render phase. StrictMode intentionally double-invokes component functions to surface impure render logic that would cause bugs in concurrent mode.

The React DevTools flamegraph chart shows the render duration of each component. Components that take longer than 16ms to render are candidates for optimization. The ranked chart sorts components by render time, making it easy to identify the most expensive components. Use these tools to guide optimization efforts rather than prematurely memoizing everything.

## Conclusion

React Fiber is a complete rethinking of how React renders. By breaking work into small units, React can prioritize updates, pause rendering, and keep the UI responsive even under heavy load. The linked-list tree structure, double buffering, and lane-based scheduling enable features like Suspense, useTransition, and automatic batching.

Understanding Fiber helps you write better React code: stable keys for efficient reconciliation, functional updates for correctness in concurrent mode, and startTransition for responsive user interfaces. It's the foundation that makes React 18's concurrent features possible.

Key takeaways:

1. **Fiber breaks rendering into interruptible units** — Small units of work that can be paused and resumed
2. **Two phases: render (interruptible) and commit (synchronous)** — Pure rendering, then DOM mutations
3. **Double buffering** — Two trees swapped atomically for consistency
4. **Lanes model** — Priority-based scheduling for different update types
5. **Suspense and transitions** — Built on Fiber's ability to pause and resume work
6. **Keys and functional updates** — Critical for correctness in concurrent mode
7. **DevTools Profiler** reveals Fiber's two-phase timing for each component
8. **React Compiler** automates memoization based on Fiber's reconciliation rules
