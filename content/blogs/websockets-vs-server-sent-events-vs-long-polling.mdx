## Introduction

Real-time communication is essential for modern web applications—chat apps, live dashboards, collaborative editing, and notifications. Three technologies dominate: **WebSockets** (bidirectional), **Server-Sent Events** (server-to-client), and **Long Polling** (compatibility fallback). Each has different trade-offs in complexity, performance, and browser support. This guide compares all three with practical implementations.

## Overview Comparison

| Feature | WebSocket | Server-Sent Events | Long Polling |
|---------|-----------|-------------------|--------------|
| Direction | Bidirectional | Server → Client | Bidirectional |
| Protocol | ws:// / wss:// | HTTP/1.1, HTTP/2 | HTTP/1.1, HTTP/2 |
| Connection | Persistent | Persistent | Repeated requests |
| Complexity | High | Low | Medium |
| Browser support | All | All (IE: polyfill) | All |
| Auto-reconnect | Manual | Built-in | Manual |
| Binary data | Yes | No (text only) | Depends |
| Max connections | ~65K per server | ~6 per domain (HTTP/1.1) | ~6 per domain |
| Firewall friendly | Sometimes blocked | Yes | Yes |

## WebSocket Implementation

WebSockets provide full-duplex communication over a single TCP connection.

### Server (Node.js)

```javascript
const WebSocket = require('ws');

const wss = new WebSocket.Server({ port: 8080 });

wss.on('connection', (ws, req) => {
  console.log('Client connected from:', req.socket.remoteAddress);

  ws.on('message', (data) => {
    const message = JSON.parse(data);
    console.log('Received:', message);

    // Echo back or broadcast
    wss.clients.forEach((client) => {
      if (client !== ws && client.readyState === WebSocket.OPEN) {
        client.send(JSON.stringify(message));
      }
    });
  });

  ws.on('close', () => {
    console.log('Client disconnected');
  });

  ws.on('error', (error) => {
    console.error('WebSocket error:', error);
  });

  // Send welcome message
  ws.send(JSON.stringify({ type: 'welcome', timestamp: Date.now() }));
});
```

### Client

```javascript
class WebSocketClient {
  constructor(url) {
    this.url = url;
    this.handlers = new Map();
    this.reconnectAttempts = 0;
    this.maxReconnectAttempts = 5;
    this.connect();
  }

  connect() {
    this.ws = new WebSocket(this.url);

    this.ws.onopen = () => {
      console.log('Connected');
      this.reconnectAttempts = 0;
    };

    this.ws.onmessage = (event) => {
      const data = JSON.parse(event.data);
      const handler = this.handlers.get(data.type);
      if (handler) handler(data);
    };

    this.ws.onclose = () => {
      console.log('Disconnected');
      this.reconnect();
    };

    this.ws.onerror = (error) => {
      console.error('Error:', error);
    };
  }

  reconnect() {
    if (this.reconnectAttempts < this.maxReconnectAttempts) {
      const delay = Math.pow(2, this.reconnectAttempts) * 1000;
      setTimeout(() => {
        this.reconnectAttempts++;
        this.connect();
      }, delay);
    }
  }

  on(type, handler) {
    this.handlers.set(type, handler);
  }

  send(data) {
    if (this.ws.readyState === WebSocket.OPEN) {
      this.ws.send(JSON.stringify(data));
    }
  }
}
```

## Server-Sent Events (SSE)

SSE provides one-way communication from server to client using standard HTTP.

### Server (Node.js)

```javascript
const http = require('http');

const server = http.createServer((req, res) => {
  if (req.url === '/events') {
    res.writeHead(200, {
      'Content-Type': 'text/event-stream',
      'Cache-Control': 'no-cache',
      'Connection': 'keep-alive',
      'Access-Control-Allow-Origin': '*',
    });

    // Send initial event
    res.write(`data: ${JSON.stringify({ type: 'connected', timestamp: Date.now() })}\n\n`);

    // Send periodic updates
    const interval = setInterval(() => {
      const data = {
        type: 'update',
        value: Math.random(),
        timestamp: Date.now(),
      };
      res.write(`data: ${JSON.stringify(data)}\n\n`);
    }, 1000);

    req.on('close', () => {
      clearInterval(interval);
    });
  }
});

server.listen(8080);
```

### Client

```javascript
class SSEClient {
  constructor(url) {
    this.url = url;
    this.handlers = new Map();
    this.connect();
  }

  connect() {
    this.eventSource = new EventSource(this.url);

    this.eventSource.onopen = () => {
      console.log('SSE connected');
    };

    this.eventSource.onmessage = (event) => {
      const data = JSON.parse(event.data);
      const handler = this.handlers.get(data.type);
      if (handler) handler(data);
    };

    this.eventSource.onerror = () => {
      console.log('SSE error, auto-reconnecting...');
    };
  }

  on(type, handler) {
    this.handlers.set(type, handler);
  }

  close() {
    this.eventSource.close();
  }
}
```

### Named Events

## Long Polling

Long polling simulates real-time by holding the HTTP response open until data is available.

### Server (Node.js)

```javascript
const http = require('http');

const pendingResponses = [];
let messageQueue = [];

const server = http.createServer((req, res) => {
  if (req.url === '/poll') {
    // If there are queued messages, send them immediately
    if (messageQueue.length > 0) {
      res.writeHead(200, { 'Content-Type': 'application/json' });
      res.end(JSON.stringify(messageQueue));
      messageQueue = [];
      return;
    }

    // Otherwise, hold the connection open
    pendingResponses.push(res);

    req.on('close', () => {
      const index = pendingResponses.indexOf(res);
      if (index > -1) pendingResponses.splice(index, 1);
    });
  }

  if (req.url === '/send' && req.method === 'POST') {
    let body = '';
    req.on('data', (chunk) => body += chunk);
    req.on('end', () => {
      const message = JSON.parse(body);

      // Send to all pending responses
      while (pendingResponses.length > 0) {
        const res = pendingResponses.pop();
        res.writeHead(200, { 'Content-Type': 'application/json' });
        res.end(JSON.stringify([message]));
      }

      res.writeHead(200);
      res.end('OK');
    });
  }
});

server.listen(8080);
```

### Client

```javascript
class LongPollingClient {
  constructor(url) {
    this.url = url;
    this.active = false;
    this.handlers = new Map();
  }

  async start() {
    this.active = true;
    while (this.active) {
      try {
        const response = await fetch(this.url);
        const messages = await response.json();

        messages.forEach((message) => {
          const handler = this.handlers.get(message.type);
          if (handler) handler(message);
        });
      } catch (error) {
        console.error('Polling error:', error);
        await new Promise((r) => setTimeout(r, 5000));
      }
    }
  }

  on(type, handler) {
    this.handlers.set(type, handler);
  }

  stop() {
    this.active = false;
  }
}
```

## When to Use Each

### Use WebSocket When:
- You need **bidirectional** communication (chat, gaming, collaborative editing)
- You need **low latency** (real-time games, financial data)
- You need to send **binary data** (file transfer, audio/video streaming)
- You're building a **high-frequency** update system

### Use SSE When:
- You only need **server-to-client** updates (notifications, live feeds, dashboards)
- You want **automatic reconnection** built in
- You need **HTTP/2 multiplexing** (multiple streams on one connection)
- You want **simpler implementation** than WebSockets

### Use Long Polling When:
- You need **maximum browser compatibility** (including very old browsers)
- Your infrastructure **blocks WebSocket** connections
- Updates are **infrequent** (every few seconds or minutes)
- You're **migrating gradually** from a polling architecture

## Hybrid Approach

Many production systems use a combination:

```javascript
class RealTimeClient {
  constructor(config) {
    this.config = config;
    this.transport = null;
  }

  async connect() {
    // Try WebSocket first
    if (this.config.enableWebSocket) {
      try {
        this.transport = new WebSocketClient(this.config.wsUrl);
        await this.transport.waitForConnection();
        return;
      } catch (e) {
        console.log('WebSocket failed, falling back to SSE');
      }
    }

    // Fall back to SSE
    if (this.config.enableSSE) {
      try {
        this.transport = new SSEClient(this.config.sseUrl);
        return;
      } catch (e) {
        console.log('SSE failed, falling back to long polling');
      }
    }

    // Fall back to long polling
    this.transport = new LongPollingClient(this.config.pollUrl);
    this.transport.start();
  }

  on(type, handler) {
    this.transport.on(type, handler);
  }

  send(data) {
    if (this.transport.send) {
      this.transport.send(data);
    } else {
      // SSE doesn't support sending, use regular HTTP
      fetch('/api/send', {
        method: 'POST',
        body: JSON.stringify(data),
      });
    }
  }
}
```

## Best Practices

1. **Start with SSE**: If you only need server-to-client updates, SSE is simpler
2. **Use WebSocket for chat/gaming**: Bidirectional communication requires WebSocket
3. **Implement fallbacks**: Use hybrid approach for maximum reliability
4. **Handle reconnection**: All transports need reconnection logic
5. **Set timeouts**: Prevent zombie connections with heartbeat/timeout

## Common Pitfalls

| Pitfall | Impact | Solution |
|---------|--------|----------|
| No reconnection logic | Users disconnected permanently | Implement exponential backoff |
| SSE on HTTP/1.1 | Connection limit (6 per domain) | Use HTTP/2 |
| WebSocket without heartbeat | Zombie connections | Implement ping/pong |
| No fallback | Blocked by firewalls | Use hybrid approach |

### Choosing the Right Technology

The choice between WebSockets, Server-Sent Events, and long polling depends on your specific requirements. Choose WebSockets when you need bidirectional communication, such as chat applications, collaborative editing, or multiplayer games. Choose Server-Sent Events when you only need server-to-client updates, such as news feeds, stock tickers, or notification systems. Choose long polling when you need compatibility with older infrastructure or when your server does not support WebSocket upgrades. Consider your server architecture, client requirements, and the nature of the data being transmitted. In many cases, a combination of technologies provides the best solution, using SSE for notifications and HTTP POST for client-to-server messages.

### Migration Strategies

Migrating between real-time technologies requires careful planning. When migrating from long polling to WebSockets, implement both protocols simultaneously and gradually switch clients to WebSocket connections. Use feature detection to check for WebSocket support before attempting to establish a connection. Implement a fallback mechanism that automatically falls back to long polling if the WebSocket connection fails. When migrating from WebSockets to SSE, convert bidirectional protocols to use SSE for server-to-client messages and regular HTTP requests for client-to-server messages. Test the migration thoroughly with realistic network conditions including high latency, packet loss, and connection interruptions to ensure that the new protocol handles edge cases correctly.

### Performance Comparison

Performance characteristics differ significantly between these technologies. WebSockets have the lowest per-message overhead because they maintain a persistent connection and use minimal framing. SSE has slightly higher overhead due to HTTP headers on each event, but the difference is negligible for most applications. Long polling has the highest overhead because each message requires a complete HTTP request-response cycle. For applications that send frequent small messages, WebSockets provide the best performance. For applications that primarily receive server updates, SSE provides comparable performance with simpler infrastructure. Long polling is suitable for applications with infrequent updates where the connection overhead is not a concern.

### Infrastructure Considerations

Your infrastructure affects which technology works best. WebSockets require servers that support long-lived connections and may need special load balancer configuration. SSE works with standard HTTP infrastructure but requires servers that support streaming responses. Long polling works with any HTTP server and standard load balancers. For cloud deployments, check whether your platform supports WebSocket connections, as some serverless platforms have connection duration limits. Consider your CDN configuration because some CDNs may buffer streaming responses, which affects SSE and long polling. Choose the technology that works best with your existing infrastructure to minimize operational complexity.

### Real-World Use Cases

Different real-world applications benefit from different real-time technologies. Slack uses WebSockets for their real-time messaging platform because they need bidirectional communication for sending and receiving messages. GitHub uses Server-Sent Events for their notification system because notifications are inherently server-to-client. Twitter uses long polling as a fallback for their timeline updates in environments where WebSockets are not available. Trading platforms use WebSockets for real-time market data because they need the lowest possible latency. News websites use Server-Sent Events for live updates because they only need server-to-client streaming. Choose the technology that matches your specific communication requirements and infrastructure constraints.

## Conclusion

Choose the right real-time technology based on your needs: WebSockets for bidirectional communication, SSE for server-to-client updates, and long polling as a compatibility fallback. In production, a hybrid approach that tries the best transport first and falls back gracefully provides the best user experience.

Key takeaways:

1. **WebSockets** are best for bidirectional, low-latency communication
2. **SSE** is simpler and has built-in reconnection for server-to-client updates
3. **Long polling** provides maximum compatibility as a fallback
4. **Hybrid approaches** combine the best of all three
5. **All transports** need reconnection and heartbeat logic for production use
