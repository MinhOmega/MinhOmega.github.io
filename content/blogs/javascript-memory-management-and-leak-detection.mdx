## Introduction

JavaScript's automatic memory management makes it easy to write code without worrying about allocation and deallocation. However, understanding how garbage collection works and recognizing memory leaks is crucial for building performant applications, especially long-running services and complex single-page applications.

This guide covers JavaScript's memory model, common memory leak patterns, and tools for detecting and preventing memory issues.

## Understanding Memory Management: Core Concepts

### JavaScript Memory Model

JavaScript manages memory through a process called garbage collection. The engine automatically allocates memory when objects are created and frees it when objects are no longer reachable.

```javascript
// Memory allocation
let user = { name: 'John', age: 30 }; // Object allocated on heap
let count = 42; // Primitive on stack

// Memory is freed when no longer reachable
user = null; // Object becomes eligible for garbage collection
```

### Stack vs Heap

**Stack**: Stores primitive values and function call frames. Fast, automatically managed.

**Heap**: Stores objects, arrays, and closures. Slower, requires garbage collection.

```javascript
// Stack allocation (primitives)
let x = 10; // Stack
let y = 'hello'; // Stack

// Heap allocation (objects)
let arr = [1, 2, 3]; // Heap
let obj = { key: 'value' }; // Heap
let fn = () => console.log('closure'); // Heap
```

### Garbage Collection Algorithms

**Mark-and-Sweep**: The most common algorithm. Starts from root objects (window, global) and marks all reachable objects. Unmarked objects are swept (freed).

**Generational Collection**: V8 divides objects into young (new) and old generations. Young objects are collected frequently, old objects less often.

## Architecture and Design Patterns

### Reference Counting

```javascript
// Reference counting example
let obj1 = { data: 'large data' }; // Reference count: 1
let obj2 = obj1; // Reference count: 2

obj1 = null; // Reference count: 1
obj2 = null; // Reference count: 0, eligible for GC
```

### Closure Memory

```javascript
// Closures retain references to outer scope
function createCounter() {
    let count = 0; // Retained by closure
    
    return {
        increment: () => ++count,
        decrement: () => --count,
        getCount: () => count,
    };
}

// count is retained as long as counter exists
const counter = createCounter();
counter.increment();
```

### WeakRef and FinalizationRegistry

```javascript
// WeakRef allows garbage collection of referenced objects
let target = { data: 'large object' };
let weakRef = new WeakRef(target);

target = null; // Object can be GC'd

// Check if still alive
if (weakRef.deref()) {
    console.log('Object still alive');
}

// FinalizationRegistry for cleanup
const registry = new FinalizationRegistry((heldValue) => {
    console.log(`Object with ${heldValue} was garbage collected`);
});

registry.register(target, 'myObject');
```

## Step-by-Step Implementation

### Detecting Memory Leaks

```javascript
// Monitor memory usage
function monitorMemory() {
    if (performance.memory) {
        const { usedJSHeapSize, totalJSHeapSize, jsHeapSizeLimit } = performance.memory;
        
        console.log({
            used: `${(usedJSHeapSize / 1024 / 1024).toFixed(2)} MB`,
            total: `${(totalJSHeapSize / 1024 / 1024).toFixed(2)} MB`,
            limit: `${(jsHeapSizeLimit / 1024 / 1024).toFixed(2)} MB`,
        });
    }
}

// Monitor periodically
setInterval(monitorMemory, 5000);
```

### Preventing Common Leaks

```javascript
// Leak 1: Event listeners not removed
class LeakyComponent {
    constructor() {
        this.handleClick = this.handleClick.bind(this);
        document.addEventListener('click', this.handleClick);
    }
    
    // Missing cleanup - memory leak!
    handleClick() {
        console.log('clicked');
    }
}

// Fixed version
class FixedComponent {
    constructor() {
        this.handleClick = this.handleClick.bind(this);
        document.addEventListener('click', this.handleClick);
    }
    
    destroy() {
        document.removeEventListener('click', this.handleClick);
    }
    
    handleClick() {
        console.log('clicked');
    }
}
```

### Closures Retaining References

```javascript
// Leak 2: Closures holding large objects
function processData() {
    const largeData = new Array(1000000).fill('x');
    
    return function process() {
        // largeData is retained even if not used
        console.log('processing');
    };
}

// Fixed: Extract only needed data
function processDataFixed() {
    const largeData = new Array(1000000).fill('x');
    const neededValue = largeData.length; // Extract only what's needed
    
    return function process() {
        console.log(`Processing ${neededValue} items`);
    };
}
```

### DOM References

```javascript
// Leak 3: Stale DOM references
class DataManager {
    constructor() {
        this.elements = new Map();
    }
    
    addElement(id, element) {
        this.elements.set(id, element);
    }
    
    // Leak: Elements removed from DOM but still in Map
    removeElement(id) {
        this.elements.delete(id); // Must explicitly remove!
    }
}

// Fixed: Use WeakMap for DOM references
class SafeDataManager {
    constructor() {
        this.metadata = new WeakMap();
    }
    
    setMetadata(element, data) {
        this.metadata.set(element, data);
    }
    
    getMetadata(element) {
        return this.metadata.get(element);
    }
}
```

## Real-World Use Cases

### Long-Running Applications

Node.js servers and Electron apps accumulate memory over time. Proper cleanup and monitoring prevent crashes.

### Single-Page Applications

React, Vue, and Angular applications must clean up subscriptions, timers, and event listeners when components unmount.

### Data Visualization

D3.js and Chart.js applications with frequent updates must manage SVG/DOM references carefully.

## Best Practices for Production

1. **Remove event listeners**: Always clean up listeners in component lifecycle hooks.

2. **Clear timers**: Use clearTimeout/clearInterval in cleanup functions.

3. **Avoid global variables**: Minimize global scope pollution.

4. **Use WeakMap/WeakSet**: For object references that should allow garbage collection.

5. **Implement cleanup patterns**: Provide destroy/cleanup methods for components.

6. **Monitor memory usage**: Use performance.memory and profiling tools.

## Common Pitfalls and Solutions

| Pitfall | Impact | Solution |
|---------|--------|----------|
| Event listeners not removed | Memory leaks | Use cleanup lifecycle hooks |
| Closures capturing large objects | Retained memory | Extract only needed values |
| DOM references in maps | Prevents GC | Use WeakMap for DOM refs |
| Timers not cleared | Continued execution | Clear in cleanup functions |

```javascript
// React cleanup example
function MyComponent() {
    useEffect(() => {
        const subscription = api.subscribe(handleData);
        const timer = setInterval(pollData, 5000);
        
        return () => {
            subscription.unsubscribe();
            clearInterval(timer);
        };
    }, []);
}
```

## Performance Optimization

### Memory-Efficient Data Structures

```javascript
// Use typed arrays for numeric data
const buffer = new ArrayBuffer(1000000 * 4); // 4MB
const int32View = new Int32Array(buffer);

// Use object pooling for frequently created objects
class Pool {
    constructor(factory, initialSize = 100) {
        this.factory = factory;
        this.pool = [];
        
        for (let i = 0; i < initialSize; i++) {
            this.pool.push(factory());
        }
    }
    
    acquire() {
        return this.pool.length > 0 ? this.pool.pop() : this.factory();
    }
    
    release(obj) {
        this.pool.push(obj);
    }
}
```

## Memory Optimization Patterns

Beyond detecting leaks, proactive memory optimization improves application performance. Use object pooling for frequently created and destroyed objects, reducing garbage collection pressure. Implement virtual scrolling for large lists, rendering only the visible items and recycling DOM nodes as the user scrolls. Use TypedArrays for numerical data, which have a fixed memory layout and can be transferred between the main thread and web workers without copying. Implement lazy loading for modules and data that are not needed on initial page load. Use WeakRef and FinalizationRegistry for cache implementations that allow the garbage collector to reclaim cached objects when memory pressure increases. Profile your application's memory usage under realistic conditions, including slow network connections and low-memory devices, to ensure it performs well across all target environments.

### Memory Profiling Workflow

Establish a systematic memory profiling workflow for your applications. Start by taking a heap snapshot before performing the action you want to analyze. Perform the action several times to amplify any memory leaks. Take another heap snapshot and compare it with the first, filtering for objects that were created but not garbage collected. Use the comparison view to identify which object types are growing and trace their retaining paths to find the source of the leak. Document common leak patterns specific to your codebase and share them with your team so that developers can avoid introducing similar leaks in the future.

### Garbage Collection Algorithms

JavaScript engines use generational garbage collection to manage memory efficiently. The generational hypothesis states that most objects are short-lived, so the engine divides the heap into young and old generations. New objects are allocated in the young generation, which is collected frequently using a scavenge algorithm. Objects that survive multiple garbage collection cycles are promoted to the old generation, which is collected less frequently using a mark-and-sweep algorithm. Understanding these algorithms helps you write code that works with the garbage collector rather than against it. Avoid creating large numbers of short-lived objects in hot code paths, as this can trigger frequent young generation collections that pause execution.

### WeakRef and FinalizationRegistry

WeakRef and FinalizationRegistry are modern JavaScript features that give developers more control over garbage collection behavior. WeakRef creates a weak reference to an object that does not prevent the object from being garbage collected. Use WeakRef to implement caches that automatically evict entries when the cached objects are no longer referenced elsewhere. FinalizationRegistry allows you to register a callback that runs when an object is garbage collected, which is useful for cleaning up external resources like file handles or network connections. These APIs require careful use because the timing of garbage collection is non-deterministic, and relying on finalization callbacks for critical logic can lead to unpredictable behavior.

### Modern Memory Management Tools

Modern browsers provide increasingly sophisticated memory management tools. Chrome DevTools includes a Memory tab with heap snapshots, allocation timelines, and allocation sampling. The heap snapshot comparison view shows objects that were created between two snapshots, making it easy to identify leaks. The allocation timeline shows memory allocations in real-time, helping you identify code that allocates memory rapidly. The allocation sampling profiler shows which functions are responsible for the most memory allocations without the overhead of a full heap snapshot. Use these tools regularly as part of your development workflow to catch memory issues early before they affect users in production.

### Best Practices for Production

Adopt memory management best practices in your production codebase. Avoid global variables that persist for the lifetime of the application. Clean up event listeners, timers, and observers when components are destroyed. Use weak references for caches that should not prevent garbage collection. Profile your application periodically to catch memory leaks before they affect users. Set up alerts for memory usage thresholds in your monitoring system. Document known memory patterns in your codebase so that new team members can avoid introducing leaks. These practices, combined with regular profiling, keep your application's memory usage stable over time.

## Conclusion

JavaScript's automatic memory management simplifies development but requires awareness of leak patterns. Monitor memory usage, clean up resources in lifecycle hooks, and use WeakMap/WeakSet for object references.

Key takeaways:
1. JavaScript uses mark-and-sweep garbage collection
2. Common leaks: event listeners, closures, DOM references
3. Always clean up subscriptions, timers, and listeners
4. Use WeakMap/WeakSet for object metadata
