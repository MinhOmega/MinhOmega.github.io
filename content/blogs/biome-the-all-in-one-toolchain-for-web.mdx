## Introduction

The modern web development toolchain is a tower of complexity. A typical project juggles ESLint for linting, Prettier for formatting, TypeScript for type checking, PostCSS for CSS processing, and various bundlers to tie it all together. Each tool has its own configuration format, plugin ecosystem, and version compatibility matrix. Biome challenges this status quo by offering a single, Rust-powered tool that handles JavaScript/TypeScript linting, formatting, and import organization with dramatically better performance.

What sets Biome apart from other attempts to unify the toolchain is its pragmatic approach. Rather than trying to replace everything at once, Biome focuses on doing the core developer workflow tasks—lint, format, sort imports—extremely well. The result is a tool that's not just faster, but simpler to configure, easier to maintain, and more consistent in its output. This guide explores Biome's capabilities for web development and how to integrate it into your existing workflow.

## Understanding Biome: Core Concepts

### The All-in-One Philosophy

Biome's core value proposition is consolidation. Instead of maintaining separate configurations for ESLint, Prettier, and import sorting plugins, you maintain a single `biome.json`. This reduces configuration drift between team members, eliminates version conflicts between plugins, and makes onboarding new developers trivial—there's one tool to learn, one configuration to understand.

### Built for the Web Platform

Biome understands modern web development idioms out of the box. It handles JSX and TSX natively, understands React hooks rules, catches accessibility issues in HTML/JSX, and formats CSS (with HTML support on the roadmap). You don't need to install framework-specific plugins for React, Vue, or Svelte—Biome's rules apply universally to the JavaScript/TypeScript layer.

### The Speed Advantage

Biome is written in Rust, which gives it a fundamental speed advantage over Node.js-based tools. On a typical web project with 500 files, Biome completes linting and formatting in under 1 second, compared to 15-30 seconds for ESLint + Prettier. This speed difference isn't just a benchmark curiosity—it changes how developers interact with their toolchain. When linting is instant, you run it after every save instead of only in CI.

## Architecture and Design Patterns

### Lossless Concrete Syntax Tree

Biome parses source code into a lossless CST that preserves every whitespace character, comment, and formatting detail. This is fundamentally different from ESLint's AST, which discards this information. The lossless tree enables Biome to make precise formatting decisions without losing track of where comments are or how blank lines separate logical sections.

### Incremental Parsing

When you change a single line in a file, Biome only re-parses the modified portion. This incremental parsing powers the language server's real-time feedback—lint errors and format suggestions appear as you type, with no perceptible delay.

### Single-Pass Pipeline

Biome's pipeline is: parse → lint → format → emit. Each stage operates on the same in-memory CST. There's no serialization between stages, no temporary files, and no redundant parsing. This single-pass architecture is why Biome is 10-20x faster than running ESLint and Prettier sequentially.

### Import Organization

Biome's import organizer groups and sorts imports according to configurable rules. It separates third-party imports from relative imports, sorts within groups, and handles type-only imports correctly. This is built into the same pipeline as linting and formatting, so there's no additional tool or plugin to install.


## Best Practices for Production

1. **Use `biome check` as your single CI command** — It runs linting, formatting, and import organization in one pass. No need for separate `eslint` and `prettier --check` commands.

2. **Configure format-on-save in your editor** — Biome's speed makes format-on-save practical. There's no perceptible delay, and it ensures every file is always properly formatted.

3. **Enable `useImportType` rule** — This enforces TypeScript's `import type` syntax, which helps bundlers tree-shake unused types and reduces bundle size.

4. **Use `overrides` for different file types** — Apply different rules to test files, configuration files, and generated code without creating separate configuration files.

5. **Commit a migration rev to `.git-blame-ignore-revs`** — After the initial migration, add the formatting commit hash to this file so `git blame` ignores the bulk formatting changes.

6. **Use `--write` for auto-fixing** — `biome check --write` auto-fixes all fixable issues. This is safe to run because Biome's auto-fixes preserve code semantics.

7. **Review nursery rules carefully** — Nursery rules are experimental and may have false positives. Enable them selectively and report issues to the Biome team.

8. **Keep the binary out of version control** — Add `node_modules/.bin/biome` to `.gitignore`. Let `npm install` handle downloading the platform-specific binary.

## Common Pitfalls and Solutions

| Pitfall | Impact | Solution |
|---------|--------|----------|
| ESLint plugins with no Biome equivalent | Missing lint rules | Keep a minimal ESLint config for gaps, check Biome's rule roadmap |
| Prettier formatting differences | Large diff on migration | Run `biome format --write .` once, commit, and use `git blame --ignore-rev` |
| Conflicting VS Code extensions | ESLint and Biome both active | Disable ESLint extension for files handled by Biome |
| Import sorting changes | Reordered imports in every file | Accept the new order, commit once, and move on |
| CSS formatting not yet complete | Limited CSS rule coverage | Use PostCSS or stylelint for CSS-specific needs until Biome's CSS support matures |

## Migrating from ESLint and Prettier

### Step-by-Step Migration Process

Migrating an existing project from ESLint + Prettier to Biome is a structured process that can be completed in a few hours for most codebases. The key is to treat it as a two-phase operation: first convert the configuration, then validate the output.

```bash
# Step 1: Install Biome alongside existing tools (don't remove ESLint yet)
npm install --save-dev @biomejs/biome

# Step 2: Use the official migration tool
npx @biomejs/biome migrate eslint --write

# Step 3: Run Biome and compare output with ESLint
npx biome lint . > biome-output.txt
npx eslint . > eslint-output.txt
diff biome-output.txt eslint-output.txt
```

### Handling Configuration Gaps

Not every ESLint rule has a direct Biome equivalent. During migration, you will encounter three categories of rules: direct equivalents (most rules), rules that Biome handles differently but covers the same concern (e.g., formatting rules), and rules with no Biome equivalent yet (typically framework-specific or niche rules).

For the third category, maintain a minimal ESLint configuration that only covers the gaps. This hybrid approach is officially supported and recommended by the Biome team. Over time, as Biome adds more rules, you can progressively remove ESLint entirely.

```json
// .eslintrc.gaps.json — only rules Biome doesn't cover yet
{
  "plugins": ["@typescript-eslint"],
  "rules": {
    "@typescript-eslint/consistent-type-imports": "off",
    "no-restricted-imports": ["error", {
      "patterns": [{ "group": ["lodash"], "message": "Use lodash-es instead" }]
    }]
  }
}
```

### Post-Migration Validation

After migrating, run a comprehensive validation to catch any regressions:

```bash
# Full check with auto-fix
npx biome check --write .

# Verify no new errors were introduced
npx biome ci .

# Check that tests still pass
npm test

# Run the build to catch any issues
npm run build
```

## Biome Language Server Protocol

### Editor Integration Architecture

Biome ships with a built-in Language Server Protocol (LSP) implementation that powers editor integrations. Unlike ESLint's language server, which runs as a separate process and communicates over stdio, Biome's LSP is optimized for real-time feedback. Diagnostics appear within 50-100 milliseconds of typing, compared to the 2-3 second delay typical of ESLint.

The language server supports the following capabilities:
- **Real-time diagnostics**: Lint errors and warnings appear as you type
- **Code actions**: Quick fixes for fixable issues, accessible via lightbulb menu
- **Format on type**: Automatic formatting when you complete a statement
- **Document highlights**: Highlight matching identifiers and keywords
- **Workspace symbols**: Search for symbols across the entire project

### JetBrains IDE Support

Beyond VS Code, Biome provides plugins for IntelliJ-based IDEs (WebStorm, IntelliJ IDEA, etc.). The JetBrains plugin supports the same features as the VS Code extension, including format-on-save, real-time diagnostics, and code actions. The plugin communicates with Biome's language server, ensuring identical behavior across all editors in a team.

```json
// WebStorm settings — configure Biome as the default formatter
{
  "formatter": "biome",
  "lintOnSave": true,
  "organizeImportsOnSave": true
}
```

## Debugging and Troubleshooting

### Diagnostic Levels and Logging

Biome provides granular control over diagnostic output, which is invaluable when debugging configuration issues or unexpected behavior:

```bash
# Show all diagnostics at the most verbose level
npx biome check --diagnostic-level=verbose .

# Debug a specific file with full trace
npx biome check --diagnostic-level=trace src/problematic-file.ts

# Show the configuration resolution path
npx biome rage
```

The `rage` command is particularly useful for troubleshooting configuration issues. It outputs the resolved configuration, installed version, platform information, and any configuration file search paths. When filing bug reports, the Biome team requests the output of `biome rage`.

### Common Migration Issues

**Import ordering conflicts**: Biome's import sorter uses different grouping rules than most ESLint import plugins. If your team has strong preferences about import grouping, configure `organizeImports` rules explicitly rather than relying on defaults.

**Formatting differences with Prettier**: Biome intentionally differs from Prettier in some formatting decisions (e.g., handling of long function parameters). These differences are documented in Biome's compatibility guide. If you cannot tolerate any formatting changes, run Biome in "Prettier-compatible" mode initially.

**Performance regressions in CI**: In rare cases, Biome's file discovery may be slower than expected in monorepos with deeply nested `node_modules`. Add explicit `files.include` patterns to limit the scope of analysis.

## Team Adoption Strategies

### Gradual Rollout

For large teams, a big-bang migration carries risk. Instead, adopt Biome gradually:

1. **Week 1**: Install Biome alongside ESLint. Run `biome check` in CI as a warning-only step.
2. **Week 2**: Enable format-on-save in VS Code for early adopters. Gather feedback.
3. **Week 3**: Fix any false positives or configuration issues. Enable Biome in CI as a blocking check for new files only.
4. **Week 4**: Enable Biome as the primary linter/formatter. Keep ESLint for any remaining gaps.
5. **Month 2**: Remove ESLint entirely if no gaps remain.

### Configuration Sharing

For organizations with multiple repositories, share Biome configuration via a published npm package:

```json
// @myorg/biome-config/biome.json
{
  "$schema": "https://biomejs.dev/schemas/1.8.0/schema.json",
  "linter": { "rules": { "recommended": true } },
  "formatter": { "indentStyle": "space", "indentWidth": 2, "lineWidth": 100 }
}
```

```json
// Project-level biome.json
{
  "extends": ["@myorg/biome-config/biome.json"],
  "linter": {
    "rules": {
      "suspicious": { "noConsoleLog": "off" }
    }
  }
}
```

This pattern ensures consistent code quality standards across all repositories while allowing project-specific overrides where necessary.

## Future Outlook

Biome's roadmap includes full CSS linting and formatting, HTML support, and potentially a bundler. The CSS support is particularly exciting for web developers—imagine linting and formatting your CSS, JavaScript, and TypeScript with the same tool and configuration.

The plugin system, planned for 2025, will allow teams to write custom lint rules in Rust or WASM. This unlocks the long tail of enterprise-specific rules that currently require custom ESLint plugins.

The broader trend is clear: the JavaScript toolchain is consolidating around Rust-based tools. Biome, Vite's Rolldown, OXC, and Rspack are all converging toward a future where a small number of fast, native tools replace the sprawling Node.js-based toolchain. Biome is the furthest along in this consolidation for the lint/format domain.
